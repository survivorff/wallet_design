# 嵌入式钱包（Embedded Wallet）：WaaS 赛道

## 一句话总结

嵌入式钱包让"钱包"从一个独立产品变成 DApp 的一个功能模块——用户不需要安装钱包，DApp 自动为他们创建。

## 嵌入式 vs 独立钱包

| | 独立钱包 | 嵌入式钱包 |
|---|---|---|
| 安装 | 需要单独安装 | 集成在 App 中 |
| 用户认知 | 知道自己有钱包 | 可能不知道 |
| Onboarding | 助记词、密码等 | 邮箱/社交登录 |
| 跨 App 使用 | 同一钱包用于多个 DApp | 每个 DApp 一个钱包（或共享） |
| 用户控制 | 完全自主 | 部分依赖 DApp |
| 体验 | 类似 Web3 | 类似 Web2 |

## 用户体验

### 传统 DApp 的 Onboarding

```
用户访问 NFT 游戏网站：
1. "您需要安装钱包"
2. 跳转到 MetaMask 下载页
3. 安装插件
4. 创建钱包，抄写助记词
5. 验证助记词
6. 回到游戏
7. 连接钱包
8. 开始玩

转化率：< 20%
```

### 嵌入式钱包的 Onboarding

```
用户访问 NFT 游戏网站：
1. 点击"开始游戏"
2. 用 Google 登录
3. 直接开始玩
（钱包在后台已经创建）

转化率：~80%
```

## 主要应用场景

### 场景一：游戏（GameFi）

```
游戏玩家不想理解：
- 助记词
- Gas 费
- 智能合约
- 链是什么

游戏需要：
- 与 Web2 游戏类似的注册流程
- 链上资产对玩家透明
- 流畅的交易体验

代表项目：Treasure DAO、Stardust、Sequence
```

### 场景二：社交应用

```
社交用户：
- 习惯邮箱/手机号登录
- 想要社交身份（不只是地址）
- 转账给朋友是核心场景

代表项目：farcaster、lens、tg botfi
```

### 场景三：消费级应用

```
NFT 票务、忠诚度计划、订阅服务等：
- 用户可能根本不知道是 Web3
- 链是后端实现细节
- 体验必须 Web2 化

代表项目：Reddit Avatars、Starbucks Odyssey、Nike .SWOOSH
```

### 场景四：金融科技

```
跨境汇款、稳定币支付：
- 用户来自传统金融用户
- 需要简单的"发送"和"接收"
- 不能要求理解技术细节

代表：各类稳定币支付应用
```

## 技术实现

### 实现方式分类

#### 方式 A：MPC 2/2

```
用户分片：存在用户设备（浏览器 IndexedDB / 移动端 Keychain）
服务商分片：存在服务商的 HSM 中

签名时：
- 双方协作生成签名
- 用户分片需要用户登录后才能解密访问

代表：Privy、Magic、Particle
```

#### 方式 B：合约钱包 + Passkey

```
用户身份：Passkey（设备生物识别）
账户：智能合约钱包（ERC-4337）
签名：Passkey 签名 P-256 → 合约验证

优势：
- 不依赖服务商存储分片
- 跨设备体验好（Passkey 同步）
- 可恢复（多 Passkey 注册）

代表：Coinbase Smart Wallet、Clave
```

#### 方式 C：托管钱包

```
私钥完全由服务商管理
用户通过传统认证（邮箱密码）控制
服务商签名所有交易

优势：体验最简单
劣势：用户没有真正的所有权（监管视角下可能算证券）

代表：早期的 Magic.link
```

### Privy

```
特点：
- 邮箱/SMS/社交登录
- MPC 2/2（自动）+ 用户可升级到自托管
- 集成简单（几行代码）
- 支持外部钱包连接（既嵌入又兼容）

定价：
- 免费：1,000 MAU
- 增长：$0.05/MAU
- 企业：定制

适合：消费级 DApp、游戏、社交
```

### Dynamic

```
特点：
- 钱包连接 + 嵌入式
- 多种登录方式
- Headless（UI 完全自定义）
- 多链支持广

定价：
- 免费：1,000 MAU
- 增长层：起步 $99/月

适合：需要灵活性的 DApp
```

### Magic

```
特点：
- 邮箱魔法链接登录
- 委托密钥管理（早期）
- 现在也支持 MPC

适合：需要简单集成的应用
```

### Web3Auth

```
特点：
- MPC 2/3（社交登录 + 设备 + 备份）
- 多种社交登录支持
- 开源 SDK

适合：需要更去中心化但仍易用的应用
```

### Particle Network

```
特点：
- 全栈钱包基础设施
- AA + MPC + 链抽象
- 提供完整的 BTC、EVM、Solana 等链支持

适合：野心大的 DApp，需要完整钱包能力
```

## 嵌入式钱包的争议

### 去中心化担忧

```
"如果 Privy 倒闭怎么办？"
"我的资产真的是我的吗？"

实际情况：
- 大多数嵌入式钱包提供"导出私钥"或"升级到自托管"选项
- 但很多用户从未导出
- 如果服务商真的消失，用户体验会很糟糕

行业回应：
- 标准化导出格式
- 第三方备份选项
- 链上恢复机制
```

### 监管风险

```
不同司法区对嵌入式钱包的看法不同：
- 是否算"托管服务"？
- 是否需要 MSB 牌照？
- 是否触发 KYC 要求？

如果被认定为托管：
- 需要金融牌照
- 需要合规流程
- 限制了产品形态
```

### 用户信任

```
传统钱包用户：
"嵌入式钱包不是真正的钱包"
"私钥不在我手里"
"这违背了 Web3 精神"

普通用户：
"啥是私钥？"
"我能用就行"

不同用户群体的接受度差异很大
```

## 未来趋势

### 趋势一：成为标准

```
嵌入式钱包正在成为新 DApp 的默认选择：
- 不集成 = 流失大量潜在用户
- 集成成本低，无理由不做

未来：DApp 同时支持嵌入式 + 外部钱包连接
```

### 趋势二：跨 DApp 共享

```
当前问题：
- 用户在 DApp A 创建嵌入式钱包
- 在 DApp B 又创建一个
- 资产分散在多个钱包

解决方向：
- 用户可以"导出"嵌入式钱包到独立 App
- 不同 DApp 间共享同一身份（用同一邮箱登录）
- 标准化的钱包数据格式
```

### 趋势三：与 Passkey 融合

```
Privy、Dynamic 等开始支持 Passkey：
- 比 MPC 更简单
- 比纯托管更安全
- 用户体验最佳

可能成为嵌入式钱包的最终形态
```

### 趋势四：监管明确

```
随着法规明确：
- 哪些操作需要牌照
- 用户保护要求
- 数据隐私规则

嵌入式钱包公司分化：
- 合规优先（欧美市场）
- 体验优先（其他市场）
- 二者兼顾的胜出
```

## 小结

嵌入式钱包是 Web3 主流化的关键基础设施。它解决了独立钱包的最大问题——Onboarding 摩擦——让 Web2 用户可以无感进入 Web3。

但它也引入了新的权衡：
- 便利 vs 自主
- 体验 vs 去中心化
- 增长 vs 合规

未来的钱包格局可能是：嵌入式钱包占据大多数普通用户，独立钱包服务专业用户和重度用户。两者通过标准协议互通，用户可以根据需求灵活选择。
