# 模块化账户与近年新玩法：7579、6900、链抽象账户、Smart EOA

## 一句话总结

2023 年之后，钱包架构进入"模块化 + 链抽象 + 智能化"的新阶段——账户不再是铁板一块，而是可插拔的模块组合；密钥不再绑死单链，而是跨链统一调度。这篇把这些散落的新范式串成一张地图。

## 为什么需要这篇

前面几篇讲了 4337（账户可编程）和 7702（存量 EOA 升级）。但 2023-2025 年钱包技术的演进远不止这两个，还有一批同样重要、但容易被忽视的新范式：

- 账户**内部**怎么组织？→ 模块化账户标准（ERC-7579 / ERC-6900）
- 账户怎么**跨链统一**？→ 链抽象账户、Keystore Rollup
- EOA 升级后叫什么？→ Smart EOA / Smart Account
- 签名怎么更安全更灵活？→ Passkey、多签验证器、Session Key 框架
- 跨链意图怎么标准化？→ ERC-7683

这篇做一张"近年新玩法地图"，把它们的定位、关系、代表项目讲清楚。

## 第一部分：模块化账户标准（账户的"插件系统"）

### 问题：早期合约钱包是"铁板一块"

```
早期的 4337 合约钱包：
- 验证逻辑、执行逻辑、恢复逻辑全部写死在一个合约里
- 想加个新功能（如新的签名方式）→ 要升级整个合约
- 不同钱包的实现互不兼容
- 一个 DApp 为钱包 A 开发的插件，钱包 B 用不了

类比：
早期合约钱包 = 不能装 App 的功能机
模块化账户 = 能自由装卸 App 的智能机
```

### 解法：把账户拆成可插拔的模块

模块化账户把一个智能账户拆成几类标准模块：

```
┌─────────────────────────────────────────────┐
│              模块化智能账户                    │
├─────────────────────────────────────────────┤
│  Validator（验证器）                          │
│  - 决定"谁有权操作"                           │
│  - 例：ECDSA 验证、Passkey(P-256) 验证、      │
│        多签验证、Session Key 验证             │
│  - 可同时装多个，不同场景用不同验证器          │
├─────────────────────────────────────────────┤
│  Executor（执行器）                           │
│  - 决定"怎么执行操作"                          │
│  - 例：批量执行、定时执行、自动化策略          │
├─────────────────────────────────────────────┤
│  Hook（钩子）                                 │
│  - 在执行前/后插入逻辑                         │
│  - 例：转账限额检查、风险拦截、记账            │
├─────────────────────────────────────────────┤
│  Fallback Handler（回退处理器）               │
│  - 处理账户未直接实现的调用                    │
└─────────────────────────────────────────────┘

效果：
- 想加 Passkey 登录？装一个 P-256 Validator 模块
- 想加每日限额？装一个 Hook 模块
- 想加 AI 自动交易？装一个 Session Key Validator + Executor
- 不需要升级整个账户，热插拔即可
```

### 两个竞争标准：ERC-7579 vs ERC-6900

模块化账户有两个主要标准，它们在竞争"模块接口的事实标准"：

| 维度 | ERC-7579 | ERC-6900 |
|------|----------|----------|
| 定位 | 最小化模块标准 | 完整的模块标准 |
| 复杂度 | 轻量、灵活 | 更严谨、更重 |
| 主要推动方 | Rhinestone、ZeroDev、Biconomy、Safe | Alchemy |
| 设计哲学 | 够用就好，把空间留给实现 | 标准化更彻底，可组合性强 |
| 模块类型 | Validator / Executor / Hook / Fallback | Validation / Execution / Hook（更细分） |
| 采用情况 | 更广（多家钱包采用） | Alchemy 生态为主 |

```
通俗理解：
- ERC-7579 像"USB 标准"——简单、通用、大家都支持
- ERC-6900 像"更严格的认证接口"——规范更全，但更重

2024-2025 年的趋势：ERC-7579 因为轻量和广泛采用，
逐渐成为模块化账户的主流标准。
```

### 模块化的价值

```
对用户：
- 按需定制账户能力（要什么装什么）
- 钱包之间迁移更容易（模块标准统一）

对开发者：
- 写一个模块，所有兼容钱包都能用
- 不用为每个钱包重复开发
- 模块市场（Module Registry）成为可能

对生态：
- 出现"模块市场"（如 Rhinestone 的 Module Registry）
- 第三方开发安全模块、自动化模块
- 类似 App Store 的生态
```

### 代表实现

```
- ZeroDev Kernel：最早的模块化账户之一，支持 7579
- Safe{Core} / Safe7579：Safe 的模块化版本
- Biconomy Nexus：7579 兼容账户
- Alchemy Modular Account：6900 标准
- Rhinestone：模块基础设施 + Module Registry
```

## 第二部分：链抽象账户（账户的"跨链统一"）

### 问题：账户被链割裂

```
现状：
- 你在 Ethereum 上的合约钱包地址：0xAAA
- 在 Arbitrum 上：可能是 0xAAA（如果用 CREATE2 同地址）
- 但每条链的账户【状态独立】
  - 密钥更新要在每条链各做一次
  - 资产分散在各链
  - 用户要管理 N 条链的账户

矛盾：
- 链越来越多（数百条 L2）
- 用户不想管理 N 个账户
- 需要"一个账户，跨链统一"
```

### 解法一：Keystore Rollup（密钥与资产分离）

```
核心思想：把"密钥管理"和"资产持有"分开

┌──────────────────────────────┐
│   Keystore Rollup（专用链）    │
│   存储：账户的密钥配置          │
│   - 谁是 owner                 │
│   - 验证规则                   │
│   - 恢复设置                   │
│   更新一次，全链生效            │
└──────────────┬───────────────┘
               │ 各链读取密钥配置
       ┌───────┼───────┬───────┐
       ▼       ▼       ▼       ▼
   Ethereum Arbitrum  Base  Optimism
   （账户）  （账户）  （账户） （账户）
   都从 Keystore 读取"我该信谁的签名"

效果：
- 想换密钥/加监护人 → 只在 Keystore Rollup 改一次
- 所有链的账户自动同步新规则
- 不用在每条链重复操作

代表：Vitalik 提出的概念，Base/OP 等在探索
```

### 解法二：跨链消息 + 统一账户层

```
通过跨链消息协议（LayerZero、Hyperlane、Axelar）：
- 账户在一条"主链"上
- 通过跨链消息控制其他链上的操作
- 用户感知是"一个账户"

代表：
- Particle Network 的 Universal Account
- Light Account 的跨链版本
```

### 解法三：意图层抽象（不在账户层，在执行层）

```
账户还是各链独立，但通过"意图 + Solver"统一体验：
- 用户表达"我要在 Base 上有 100 USDC"
- Solver 网络处理跨链的复杂性
- 用户感知是统一的

这部分详见 09-future/01-chain-abstraction.md 和 02-intent-driven.md
```

### 三种路径对比

| 路径 | 抽象层级 | 成熟度 | 代表 |
|------|---------|--------|------|
| Keystore Rollup | 密钥层 | 早期 | Base/OP 探索中 |
| 跨链消息统一账户 | 账户层 | 发展中 | Particle、LayerZero |
| 意图 + Solver | 执行层 | 较成熟 | Across、UniswapX |

## 第三部分：Smart EOA（7702 催生的新物种）

```
7702 之后出现了一个新概念：Smart EOA（智能 EOA）

定义：
- 一个委托到合约实现的 EOA
- 地址是 EOA 的，但行为像合约钱包
- 介于"纯 EOA"和"纯合约钱包"之间

特点：
- 拥有 EOA 的历史和地址
- 拥有合约钱包的能力（批量、代付、模块）
- 但保留 EOA 私钥（双重控制，有利有弊）

意义：
- 这是存量用户进入 AA 世界的主要形态
- 2025 年后，"Smart EOA" 可能成为主流账户类型
- 钱包需要区分对待：纯 EOA / Smart EOA / 纯合约钱包
```

详见本章 [12-eip-7702-deep-dive.md](./12-eip-7702-deep-dive.md)。

## 第四部分：签名与验证的新玩法

### Passkey / WebAuthn 验证器

```
模块化账户的一个杀手级 Validator：
- 用设备生物识别（Face ID/指纹）替代助记词
- 私钥（P-256）在设备安全芯片
- 合约用 P-256 Validator 验证签名

代表：Coinbase Smart Wallet、Clave
详见 09-future/05-passkey-webauthn.md
```

### Session Key（会话密钥）框架

```
一个受限的临时密钥，授权给 DApp/AI Agent：
- 时间限制（如 24 小时）
- 金额限制（如 ≤ 1000 USDC）
- 目标白名单（只能与某些合约交互）
- 操作限制（只能 swap，不能转账）

应用：
- 游戏：免确认的高频操作
- AI Agent：自主执行但有边界
- DApp：一次授权，多次操作

标准化：Session Key 正在通过模块化标准（7579 Validator）统一
详见 09-future/03-ai-agent-wallets.md
```

### 多签验证器 / 社交恢复模块

```
模块化后，多签和社交恢复成为"可装的模块"：
- 多签 Validator：N/M 签名才能执行
- 社交恢复 Module：监护人帮助恢复
- 时间锁 Hook：大额操作延迟执行

不再需要专门的"多签钱包"——
任何模块化账户装上对应模块即可
```

## 第五部分：跨链意图标准 ERC-7683

```
问题：
- 各跨链桥/意图协议格式不统一
- 用户的"跨链意图"无法在不同协议间通用

ERC-7683：标准化跨链订单格式
- 统一"我要从 A 链的 X 换到 B 链的 Y"的表达
- 不同 Solver/桥可以竞争解决同一个意图
- 钱包可以聚合多个跨链方案

意义：
- 让链抽象的"意图层"有了统一标准
- 推动方：Uniswap、Across 等
```

## 这些玩法对钱包产品意味着什么

### 对钱包开发者

```
1. 拥抱模块化标准（优先 ERC-7579）
   - 不要再写"铁板一块"的合约钱包
   - 复用生态的模块
   - 让自己的账户能装第三方模块

2. 支持 Smart EOA（7702）
   - 让存量用户一键升级
   - 这是获取存量用户的关键

3. 准备链抽象
   - 用户不想管理 N 条链
   - 至少做到"统一余额 + 自动路由"

4. Passkey + Session Key 是标配
   - Passkey 解决 Onboarding
   - Session Key 解决自动化/agentic
```

### 对用户

```
理解你的账户类型：
- 纯 EOA：老地址，无 AA 能力
- Smart EOA：7702 升级后，有 AA 能力但保留私钥（注意私钥风险）
- 纯合约钱包：完整 AA，私钥保护强
- MPC：分片管理

选择取决于你的需求和资产规模
```

### 对投资人/分析师

```
评估一个钱包项目的技术先进性，看：
- 是否采用模块化标准（7579/6900）
- 是否支持 7702（存量用户接入）
- 是否有链抽象能力
- Passkey + Session Key 是否到位

这些是 2025 年后的"技术基准线"
没有这些 = 技术落后
```

## 小结

2023-2025 年，钱包架构从"单一合约"演进到"模块化 + 链抽象 + 智能化"的新范式：

1. **模块化账户（7579/6900）**：账户变成可插拔的模块组合，7579 渐成主流
2. **链抽象账户**：通过 Keystore Rollup / 跨链消息 / Solver，让账户跨链统一
3. **Smart EOA（7702）**：存量 EOA 升级后的新物种，介于 EOA 和合约钱包之间
4. **签名新玩法**：Passkey 验证器、Session Key 框架成为标配模块
5. **跨链意图标准（7683）**：让链抽象的意图层有统一标准

这些玩法不是孤立的，而是层层拼合成一个完整的栈（见全景图）。理解它们的关系，才能看懂 2025 年以后钱包技术的全貌——以及判断一个钱包项目是站在技术前沿还是已经落后。
