# 自托管的真相：从助记词到 TEE 钱包的架构光谱

## 一句话总结

"自托管"不是一个是非题，而是一个光谱——判断一个钱包是否真正自托管，不看它怎么登录，而看私钥在谁手里、服务商关停后你还能不能动你的钱。

## 为什么需要这篇

钱包行业最大的概念混乱，就是把"用户体验"和"密钥架构"混为一谈。

- "邮箱登录" 是**入口体验**
- "自托管" 是**密钥架构**

这两者完全正交。同样是"邮箱登录给你分配一个钱包"，背后可能是完全托管、半托管、或真正的自托管。很多产品在营销时刻意模糊这条界线，用"self-custody"当卖点，但实现上其实是"看不见明文的高级托管"。

这篇文章建立一个清晰的判定框架，并对照剖析当前最火热的几种钱包架构——包括最新的 TEE-based / agentic wallet 路线。

## 第一性原理：自托管到底是什么

### 经典定义

```
自托管（self-custody / non-custodial）：
私钥完全由用户掌控，没有任何第三方能够：
1. 读取你的私钥（保密性）
2. 动用你的资产（控制权）
3. 阻止你使用你的资产（可用性 / 抗审查）
```

注意这里有**三个独立的维度**，大多数关于自托管的争论都源于只盯着其中一个：

| 维度 | 含义 | 反面 |
|------|------|------|
| 保密性 | 别人**看不到**你的私钥 | 私钥泄露 |
| 控制权 | 别人**动不了**你的资产 | 被盗用 |
| 可用性 | 别人**停不了**你用资产 | 被冻结/服务中断 |

**真正的自托管，三个维度都要满足。** 很多"半自托管"方案只满足了前两个（服务商看不到也偷不走），但栽在第三个（服务商一关停，你就动不了钱）。

### 判定自托管的三个灵魂问题

不管一个钱包的架构多花哨、营销话术多漂亮，问这三个问题就能定性：

```
Q1. 你能独立导出并使用私钥/助记词吗？
    能 → 至少有完整自托管的出口
    不能 → 控制权存疑

Q2. 服务商彻底关停/跑路/被监管冻结后，
    你能否用自己手里的东西恢复并签名转走资产？
    能 → 满足可用性，是真自托管
    不能 → 是托管或半托管（无论它怎么宣传）

Q3. 控制权事实上挂在什么凭证上？
    挂在你独占的密钥 → 自托管
    挂在邮箱/社交账号（Web2 凭证）→ 有托管色彩
    （因为邮箱被盗 = 钱包被盗，且邮箱由第三方控制）
```

**Q2 是生死线。** 一个钱包能不能叫自托管，本质上就看这一条。

## 第二部分：主流钱包架构光谱

把当前所有火热的钱包架构按"自托管程度"排成一条光谱：

```
托管 ←──────────────────────────────────────────────→ 完全自托管
    
完全托管   2/2 MPC    TEE-custody   2/3 MPC   Passkey+AA   助记词/硬件
(交易所)   (Privy)    (Turnkey类)   (Web3Auth) (Coinbase    (MetaMask/
                                              Smart Wallet)  Ledger)
   ❌        🟡          🟡           🟢          ✅           ✅
```

下面逐个拆解，重点标注每种架构对三个灵魂问题的回答。

### 架构 1：完全托管（不是自托管）

```
邮箱登录 → 服务商生成并完整保管私钥 → 服务商替你签名

代表：早期 Magic.link、交易所内置钱包、部分 Web2 风格钱包
```

| 灵魂问题 | 回答 |
|---------|------|
| Q1 能导出私钥? | ❌ 通常不能 |
| Q2 服务商关停能否自救? | ❌ 不能 |
| Q3 控制权挂在? | 服务商的账户系统 |

**定性：托管。** 和在交易所开户没本质区别，只是体验包装成了"钱包"。

### 架构 2：2/2 MPC（半托管，当前最常见）

```
私钥拆成两片（门限签名 TSS）：
  分片 A：用户设备（登录后解密）
  分片 B：服务商服务器
签名时双方协作，完整私钥从不出现

代表：Privy（默认）、Magic（演进后）、部分 Particle 配置
```

| 灵魂问题 | 回答 |
|---------|------|
| Q1 能导出私钥? | 🟡 部分支持"导出"（把两片合成） |
| Q2 服务商关停能否自救? | ❌ 你只有一片，单独签不了 |
| Q3 控制权挂在? | 用户分片 + 服务商分片，共同控制 |

**定性：半托管（semi-custodial）。** 比完全托管强——服务商单独偷不走你的钱（只有一片）。但你也单独动不了（也只有一片），可用性依赖服务商在线。监管对这类的定性仍在争论。

> 这是"邮箱登录钱包"最常见的真实形态，也是最容易被包装成"self-custody"的一种。严格说它不满足 Q2。

### 架构 3：TEE-custody（本文重点，agentic wallet 主流路线）

```
邮箱登录 → 服务端 TEE（可信执行环境）内生成/解密助记词
助记词明文只在 TEE 飞地（enclave）内存在
飞地外（包括服务商运维）看到的都是密文
TEE 内完成派生、签名、甚至自动化策略执行

代表：Turnkey、Phala、Lit Protocol，及一批 2024-2025 的
      "agentic wallet" / "意图钱包" 项目
TEE 技术：Intel SGX/TDX、AMD SEV、AWS Nitro Enclave
```

这是你那张方案图里的架构，单独开一节深拆（见第三部分）。先给定性：

| 灵魂问题 | 回答 |
|---------|------|
| Q1 能导出私钥? | 取决于设计，部分支持 |
| Q2 服务商关停能否自救? | ⚠️ **多数实现：不能**（TEE 在服务商机房） |
| Q3 控制权挂在? | TEE 访问权 → 通常挂在邮箱凭证 |

**定性：TEE-custody（飞地托管）。** 服务商运维**读不到**明文（保密性强，比 2/2 MPC 还强），但 TEE 在它的服务器上，可用性依赖它。介于半托管和自托管之间，偏自托管一侧——但"任何第三方无法接触"是夸大：无法**读取** ≠ 无法**影响可用性**。

### 架构 4：2/3 MPC（基本算自托管）

```
私钥拆三片：用户设备 + 服务商 + 用户备份（另一设备/云）
任意两片即可签名

代表：Web3Auth（Torus）
```

| 灵魂问题 | 回答 |
|---------|------|
| Q1 能导出私钥? | 🟡 可重组 |
| Q2 服务商关停能否自救? | ✅ 用"设备 + 备份"两片即可，不依赖服务商 |
| Q3 控制权挂在? | 三片，用户掌握多数 |

**定性：基本算自托管。** 关键突破在 Q2——服务商不可用时，用户用自己的两片就能恢复。这是和 2/2 的本质区别。

### 架构 5：Passkey + 合约钱包（真自托管 + 最好体验）

```
邮箱/Passkey 登录 → 设备生物识别（Face ID/指纹）
私钥（P-256）在设备安全芯片（Secure Enclave/StrongBox）生成
私钥永不离开硬件，服务商从未接触
合约钱包（ERC-4337）在链上验证 P-256 签名

代表：Coinbase Smart Wallet、Clave
```

| 灵魂问题 | 回答 |
|---------|------|
| Q1 能导出私钥? | 私钥在安全芯片不可导出，但有合约层的恢复 |
| Q2 服务商关停能否自救? | ✅ 私钥在你设备，合约在链上，服务商无关 |
| Q3 控制权挂在? | 你设备的安全芯片 + 合约钱包的 owner |

**定性：真自托管。** 而且打破了"自托管必然难用"的旧假设——体验像 Web2，本质是自托管。代价是引入对 Apple/Google（Passkey 同步）的依赖，和对 AA 基础设施的依赖。

### 架构 6：助记词 / 硬件钱包（经典自托管）

```
助记词钱包：私钥派生自用户保管的助记词（MetaMask、Rabby）
硬件钱包：私钥在物理设备的 SE 芯片，永不触网（Ledger、Trezor）
```

**定性：最纯粹的自托管。** 三个维度全满足，但全部责任也在用户身上（丢了就没了）。

### 一张总表

| 架构 | 保密性 | 控制权 | 可用性(Q2) | 体验 | 定性 |
|------|--------|--------|-----------|------|------|
| 完全托管 | ❌ | ❌ | ❌ | 极好 | 托管 |
| 2/2 MPC | ✅ | 🟡 | ❌ | 极好 | 半托管 |
| TEE-custody | ✅✅ | 🟡 | ⚠️ | 极好 | 飞地托管 |
| 2/3 MPC | ✅ | ✅ | ✅ | 好 | 基本自托管 |
| Passkey+AA | ✅✅ | ✅ | ✅ | 极好 | 自托管 |
| 助记词/硬件 | ✅✅ | ✅ | ✅ | 差/中 | 纯自托管 |

## 第三部分：深拆 TEE-custody 架构

因为这是当前 agentic wallet 最火的路线，也是最容易在"是否自托管"上产生误导的，单独深入。

### 它长什么样

```
┌─────────────────────────────────────────────────────┐
│  用户：邮箱登录（OAuth / 验证码），无需安装 APP       │
└───────────────────────┬─────────────────────────────┘
                        │ 认证通过
                        ▼
┌─────────────────────────────────────────────────────┐
│  服务端 TEE 飞地（SGX / TDX / Nitro Enclave）        │
│  ┌─────────────────────────────────────────────┐    │
│  │  飞地内（外部包括运维都看不到明文）：         │    │
│  │  - 解密/生成助记词（明文仅存在于此）          │    │
│  │  - 派生私钥                                   │    │
│  │  - 签名交易                                   │    │
│  │  - 运行自动化 / 意图 / agentic 策略           │    │
│  └─────────────────────────────────────────────┘    │
│  Remote Attestation：向用户证明"我跑的是开源那份代码"│
└─────────────────────────────────────────────────────┘
```

### 为什么 agentic wallet 必然走向服务端 TEE

把那张方案图的几个卖点连起来看，会发现它们**共同指向服务端 TEE**，几乎排除了"私钥只在用户本地"的可能：

```
"无需安装 APP / 插件"
  → 没有可靠的本地密钥安全存储载体（浏览器 localStorage 不安全）

"Automation Wallet / agentic 交易"
  → 需要在用户离线时也能自动签名
  → 密钥必须活在一个【常在线】的环境里
  → 用户设备做不到常在线 → 必须服务端

"SOC 2 Type 2"
  → 这是【托管式 SaaS】的合规审计标准
  → 纯自托管钱包根本不需要 SOC 2（服务商不碰用户数据）
  → 强调它 = 承认在运营触及敏感操作的后端

三条证据交叉验证 → 几乎一定是服务端 TEE 架构
```

> 这里有个隐藏的内在矛盾值得记下来：**"agentic 自动交易"和"纯自托管"在物理上是冲突的**。要让钱包在你睡觉时自动执行策略，密钥就必须在一个你不在场也能签名的地方——这天然要求把签名能力托付给一个常在线的环境。鱼和熊掌很难兼得，TEE 是当前对这个矛盾"最不坏"的折中。

### 它的 self-custody 主张：一半成立，一半话术

方案图原话："用户明文助记词只存在于用户端上和 TEE 内，任何第三方服务无法接触。"

**成立的部分** ✅

如果 TEE 实现正确 + Remote Attestation 可验证 + 代码开源：
- 服务商的**运维人员确实读不到明文助记词**
- 这在保密性上比 2/2 MPC、明文托管都强
- "服务商作恶偷币"这个风险被显著降低

**话术 / 风险的部分** ⚠️

1. **可用性依赖服务商（致命点，对应 Q2）**
   TEE 在它的服务器。它关停/跑路/被监管，你还能签名吗？如果不能 → 不满足自托管的"可用性"维度。"任何第三方无法接触"说的是**读取**，但**没说停服**。

2. **信任根没有消除，只是转移了**
   你不再需要信任"服务商不偷看"，但你现在必须信任：
   - TEE 硬件厂商（Intel/AMD/AWS）没有后门
   - TEE 没有未知漏洞——SGX 历史上被侧信道攻击破过多次（Foreshadow、SGAxe、ÆPIC Leak 等）
   - 它跑的真是开源那份代码（靠 attestation，但**用户真的会去验证吗**？默认不验证 = 信任假设回到服务商）

3. **"助记词在用户端"那半句要打问号**
   如果完整助记词真在用户端，agentic 自动交易怎么在用户关闭浏览器后继续？大概率助记词**主要活在服务端 TEE**，用户端那份是可选备份，甚至是营销修辞。

4. **控制权事实上挂在邮箱（对应 Q3）**
   "邮箱登录 → 重新获得 TEE 内密钥的访问权"。那么**邮箱被盗是否等于钱包被盗**？如果是，控制权就事实上挂在一个 Web2 凭证上，而这个凭证由邮件服务商控制——这是强托管色彩。

### 诚实的定性

```
严格定义（私钥只在用户掌控 + 服务商停了我照样能动钱）：
  → ❌ 不满足。这是 TEE-custody / 飞地托管

宽松定义（服务商无法读取/盗用你的明文密钥）：
  → 🟡 满足，且确实比 2/2 MPC、明文托管更强

最准确的说法：
  → "TEE-based non-custodial"（基于 TEE 的非托管）
  → 介于半托管和自托管之间，偏自托管一侧
  → 但宣称"完全 self-custody / 任何第三方无法接触"是夸大
```

### 要让 TEE 钱包真正配得上"自托管"，必须回答

```
1. 服务商跑路后，用户能否用【本地备份】独立恢复并签名？
   （这是 Q2 生死线。能 → 理直气壮叫非托管；不能 → 高级托管）

2. 邮箱被盗能否直接接管钱包？
   （能 → 控制权挂在 Web2 凭证，托管色彩重）

3. Remote Attestation 是否【默认强制】对用户验证，
   还是只在文档里写写？
   （不强制验证 = 信任假设退回到"相信服务商"）

4. 单一 TEE 还是多 TEE 冗余 / TEE + MPC 混合？
   （单一 TEE = 单点信任 + 单点漏洞风险）
```

一个负责任的 TEE 钱包，理想形态是 **TEE + 用户本地备份分片 + 多重恢复**——让"读不到"和"停不了"两个维度都成立。

## 第四部分：那张方案图的逐条复核

把图里 6 个卖点放到上面的框架里复核一遍：

| # | 卖点 | 可达性 | 批注 |
|---|------|--------|------|
| 1 | 便捷（邮箱登录无助记词） | ✅ | 入口体验，与密钥架构解耦，真实可达 |
| 2 | 安全（开源 + SOC 2 Type 2） | 🟡 | 开源值得肯定；但 SOC 2 恰恰暴露了"托管式后端"的存在 |
| 3 | self-custody（助记词只在用户端 + TEE） | 🟡 | **TEE-custody，非严格自托管**；保密性强，可用性存疑 |
| 4 | 无需插件/APP | ✅ | Web + 服务端 TEE 即可，但这也反推出密钥在服务端 |
| 5 | Automation / 意图 / agentic | ✅ | 可达，但与"纯自托管"物理冲突，是走向服务端 TEE 的根因 |
| 6 | 快捷链上支付 | ✅ | 工程问题，非密钥架构问题 |

**整体判断：** 这是一个**体验优先、TEE 托管密钥、主打 agentic 自动化**的钱包方案。它在保密性和体验上确实有竞争力，定位也很清晰（agentic / 自动化交易这个赛道 TEE 几乎是必选项）。但把它定性为"完全 self-custody"是不准确的——更诚实的标签是"TEE-based non-custodial wallet"。卖点 2 和卖点 3 之间存在张力（SOC 2 暗示托管运营，self-custody 暗示用户主权），需要在产品话术上想清楚怎么自洽。

## 第五部分：一个更优实现——"客户端签名 + TEE 仅在创世"

前面第三部分剖析的是"**纯服务端 TEE 签名**"路线——密钥常驻飞地，每笔交易都进飞地签名。但 TEE 钱包还有一种**明显更优**的实现路线，它把 TEE 的角色从"每笔交易的签名者"降级为"一次性的密钥铸造者"。理解这个差异，是判断一个 TEE 钱包成色的关键。

### 这个改进型架构长什么样

```
1. 客户端把 邮箱 + 密码 + 安全码，经端对端加密信道发给 TEE
2. TEE 内：生成密钥对，生成并加密助记词
3. 加密后的助记词缓存到服务端数据库（密文）
4. TEE 把【派生出的多链私钥】用【用户的公钥】加密后，下发回客户端
5. 客户端【本地】用私钥签名 → 直接与 Solana / Ethereum 交互
```

```
   用户端                                    TEE（仅创世时介入）
  ┌────────┐   1. 邮箱/密码/安全码(E2E)    ┌──────────────┐
  │        │ ───────────────────────────→ │  生成密钥对   │
  │        │                              │  加密助记词   │
  │        │   4. 公钥加密的多链私钥        │              │
  │  本地   │ ←─────────────────────────── │              │
  │  签名   │                              └──────┬───────┘
  │        │                                     │ 3. 加密助记词缓存
  │        │                                     ▼
  └───┬────┘                              ┌──────────────┐
      │ 5. 私钥本地签名                     │   服务端 DB   │
      ▼                                    │  （只有密文）  │
  Solana / Ethereum                       └──────────────┘
```

### 和"纯服务端 TEE 签名"的本质区别

最关键的一点：**签名发生在客户端（第 5 步），TEE 不在每笔交易的热路径上。** TEE 只在"开户 / 生成密钥"这一次性环节出现。

| 维度 | 客户端签名 + TEE 创世 | 纯服务端 TEE 签名 |
|------|---------------------|------------------|
| 签名位置 | ✅ 客户端 | ❌ 服务端飞地 |
| 私钥是否到用户手里 | ✅ 是（公钥加密下发） | ❌ 一直在飞地 |
| 运维能否读私钥 | ✅ 不能 | 不能 |
| **服务商挂了能否动钱** | 🟢 **能（私钥已在本地）** | ❌ 不能 |
| TEE 攻击面 | 只在开户时暴露 | 持续暴露 |
| agentic 自动化 | ⚠️ 需额外机制（见下） | ✅ 天然支持 |

**这个区别直接改变了自托管定性**：因为第 4 步之后用户本地已握有可用私钥，可以独立完成签名转走资产——**自托管的生死线 Q2（服务商关停能否自救）基本守住了**。这一路线可以正当地主张 non-custodial，比纯服务端 TEE 签名强一个档次。

### 但它和"纯本地钱包"仍有两点差距

不要因此就把它等同于 MetaMask / 硬件钱包。它和"纯本地自托管"的本质差异在于信任根：

```
纯本地钱包（MetaMask）：
  助记词在【你的设备】生成，明文从不触及任何服务器
  信任根 = 你自己

这个方案：
  助记词在【TEE 飞地】生成（第 2 步），生成那一刻明文存在于服务端
  密码也上行到了 TEE（第 1 步）
  信任根 = 你 + 一个可验证的 TEE 黑盒
```

两个具体的打问号点：

1. **创世信任**：你必须信任"TEE 生成助记词的那一瞬间，没有偷偷记录/外传"。这个信任**可以**靠开源 + 可复现构建 + 默认强制的 Remote Attestation 来兑现——做到了，差距很小；没做到，就退回"相信公司"。

2. **密码上行**：第 1 步密码离开了设备。更干净的设计应是密钥对在客户端从密码派生、只上行公钥、密码永不出设备。密码上行意味着密码的保密性也依赖 TEE 完整性，且若解密密钥从密码派生，则整个钱包安全性 = 密码强度。

### 一个微妙但要命的区分：抢救资金 ≠ 导出助记词

很多人把这两件事混为一谈，但它们依赖的东西不同：

```
抢救资金：第 4 步后私钥已在本地 → 服务商挂了也能签名转走  ✅ 成立
导出助记词（多链总根）：加密助记词 blob 缓存在【服务端】(第 3 步)
   → 若本地没存这份 blob，"导出助记词"仍需从服务器拉取
   → 服务器真的没了：能靠已下发的私钥抢救 funds，
     但未必能拿回"助记词"这个多链总根
```

所以"用户可本地导出助记词、不走后端"这句话要完全成立，必须满足：**那份加密助记词 blob 也有一份在客户端本地（或用户能独立持有），且开源代码能在本地完成解密。** 如果 blob 只在服务器，那"导出助记词"严格说仍依赖服务器在线——尽管"抢救资金"不依赖。这是细微但要命的区别。

### 和 agentic 卖点的内在矛盾

如果这个方案同时主打"Automation / agentic 自动交易"（前一张方案图的卖点 5），会和"客户端签名"物理冲突：

```
客户端签名 → 用户关机/离线时没人能签 → 自动化做不了
要做 agentic 自动化 → 必须有个【常在线】的地方能签：
   方案 A：TEE 保留一份可用私钥副本
           → 那"私钥只在客户端"就不准确了
   方案 B：用独立的 session key 委托
           → 主钱包仍在客户端，自动化用受限的委托密钥
           → 这是更干净的解法
```

判断标准：**它的自动化用的是主私钥（那 self-custody 主张打折）还是独立 session key（那主张成立）。** 这是评估时必须问清楚的。

### 评估这类钱包的核验清单

不管它怎么宣传，逐条问这些，就能定性：

```
□ 用户解密用的密钥对在哪生成？密码是否必须上行到 TEE？
   （理想：客户端派生，只上行公钥，密码不出设备）
□ 加密助记词 blob 是否有一份在客户端本地？
   （决定"服务商消失后能否导出助记词"，而非只抢救资金）
□ TEE 代码是否开源 + 可复现构建（reproducible build）？
□ 客户端是否【默认强制】验证 Remote Attestation？
   （不强制 = 飞地可被偷换 = 安全归零）
□ agentic 自动化用的是主私钥还是独立 session key？
   （关系到"私钥只在客户端"这句是否成立）
□ 单一 TEE 还是多 TEE / TEE+MPC 混合？侧信道风险怎么对冲？
```

### 小结这一节

```
"客户端签名 + TEE 仅在创世" vs "纯服务端 TEE 签名"：

前者 > 后者：
  签名在客户端、私钥下发到用户手里
  → 守住了 Q2（服务商挂了能抢救资金）
  → 可以合理称为 non-custodial

前者 < 纯本地钱包：
  助记词的【创世】在 TEE 完成、密码上行
  → 信任根是"我 + 可验证的 TEE 黑盒"，不是"纯粹的我自己"

最终成色取决于实现细节（见核验清单）：
  开源 + 默认强制 attestation + 本地留 blob + session key 做自动化
  → 这几条做到 → 配得上 self-custody
  → 有一条没做到 → 滑向"包装得好的半托管"
```

这也回到全文的核心论点：**一个 TEE 钱包是不是真自托管，不取决于它用没用 TEE，而取决于它有没有给用户留一条不依赖服务商的逃生路径。**

## 给不同读者的 takeaway

### 如果你是用户

- 看到"邮箱登录 / 无需助记词 / self-custody"，别被体验迷惑，往下挖一层：**私钥在哪、服务商停了我还能不能动钱**
- 小额、日常、要 agentic 自动化 → TEE/MPC 钱包够用，便利值这个价
- 大额、要绝对主权 → 用 Passkey+AA、2/3 MPC，或硬件钱包
- 永远问一句：**这家公司倒了，我的钱还拿得回来吗？**

### 如果你是建设者

- 不要滥用 "self-custody" 标签——用户和监管迟早会较真
- 如果走 TEE 路线，把"服务商跑路后用户能自救"做成真功能（本地备份分片），而不是文档里的一句话
- Remote Attestation 要做成**默认对用户可验证**，否则信任假设等于退回托管
- 考虑 **TEE + MPC 混合**：用 TEE 解决 agentic 常在线签名，用用户持有的分片守住可用性底线

### 如果你是投资人/分析师

- "邮箱钱包"是体验词，不是架构词，尽调时必须穿透到密钥架构
- agentic wallet 赛道，TEE 几乎是绕不开的选择——但要区分"真做了用户可自救"还是"只是看不见明文的托管"
- SOC 2 / 开源 / TEE 这些词同时出现时，警惕它们之间的内在矛盾

## 小结

"自托管"被严重滥用了。判断一个钱包是不是自托管，记住三个维度（保密性、控制权、**可用性**）和一条生死线（**服务商关停后你能否独立动用资产**）。

当前钱包架构是一条光谱：从完全托管，经 2/2 MPC、TEE-custody、2/3 MPC，到 Passkey+AA 和硬件钱包，自托管程度递增。最火的"邮箱登录 + agentic 自动化"方案，技术上几乎必然落在 **TEE-custody**——它保密性很强、体验极好，但因为密钥活在服务商的飞地里、可用性依赖服务商，严格说是"TEE-based 非托管"而非完全自托管。

这不是说 TEE 钱包不好——对 agentic 这个赛道它可能是最优解。而是说：**用对名字，讲清楚信任边界，比用一个漂亮但不准确的标签更重要。**
