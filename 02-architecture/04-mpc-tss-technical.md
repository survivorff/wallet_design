# MPC/TSS 技术原理：密钥不在一处的安全哲学

## 一句话总结

MPC 让多方在不暴露各自秘密的前提下共同完成计算——应用到签名领域，就是让私钥从头到尾不以完整形态存在于任何地方。

## MPC 的一般概念

### 什么是安全多方计算

MPC（Secure Multi-Party Computation）解决的问题：

> n 个参与方各自持有私密输入 x₁, x₂, ..., xₙ，他们想共同计算 f(x₁, x₂, ..., xₙ) 的结果，但不想让任何人知道其他人的输入。

经典例子：百万富翁问题
- Alice 和 Bob 想知道谁更有钱
- 但都不想告诉对方自己有多少钱
- MPC 可以在不暴露具体数字的情况下得出"谁更有钱"的结论

### 应用到数字签名

在钱包场景中：
- 私密输入 = 各方持有的密钥分片
- 计算函数 = 数字签名算法
- 输出 = 有效的数字签名
- 安全保证 = 没有任何一方能获得完整私钥

## TSS 的核心协议

### 阶段一：分布式密钥生成（DKG）

目标：n 个参与方共同生成一个公钥，每方获得一个密钥分片，完整私钥从未出现。

#### Feldman VSS（可验证秘密分享）

```
设置：3 方参与，门限 t=2

1. 每方 Pᵢ 选择随机多项式 fᵢ(x) = aᵢ₀ + aᵢ₁x（1 次多项式，因为 t-1=1）

2. 每方计算并广播承诺：
   Cᵢ₀ = aᵢ₀ × G
   Cᵢ₁ = aᵢ₁ × G

3. 每方 Pᵢ 秘密发送 fᵢ(j) 给 Pⱼ（j ≠ i）

4. 每方验证收到的分片：
   fᵢ(j) × G == Cᵢ₀ + j × Cᵢ₁ ?

5. 每方计算自己的最终分片：
   sⱼ = Σᵢ fᵢ(j)

6. 公钥 = Σᵢ Cᵢ₀ = (Σᵢ aᵢ₀) × G

结果：
- 公钥已知（所有人都能计算）
- 私钥 = Σᵢ aᵢ₀（从未被任何人完整持有）
- 每方持有分片 sⱼ（私钥在点 j 处的值）
```

#### 为什么安全

- 每方只知道自己的分片 sⱼ
- 任何少于 t 个分片无法重构私钥（Shamir 秘密分享的性质）
- 承诺机制防止参与方作弊（发送错误分片会被检测到）

### 阶段二：门限签名

以 ECDSA 的 TSS 为例（简化版，基于 GG20 协议思路）：

```
参与方：P₁ 持有分片 s₁，P₂ 持有分片 s₂（2/3 门限中的两方）

目标：生成签名 (r, s)，其中 s = k⁻¹(e + r·d) mod n
      e = 消息哈希，d = 完整私钥，k = 签名随机数

挑战：
- 没有人知道完整的 d
- 没有人知道完整的 k
- 需要计算 k⁻¹ 和 k⁻¹·d，但这些都涉及乘法（非线性）

解决方案（多轮交互）：

Round 1: 生成分布式随机数 k
- P₁ 选择 k₁，P₂ 选择 k₂
- 使用加法秘密分享：k = k₁ + k₂
- 计算 R = k × G（通过 MPC 协议，不暴露 k₁, k₂）
- r = R.x mod n

Round 2: 计算签名值 s
- 需要计算 k⁻¹ × (e + r × d)
- 使用乘法转换协议（Multiplicative-to-Additive, MtA）
- P₁ 和 P₂ 交互，各自获得 s 的加法分片 s₁, s₂
- s = s₁ + s₂ mod n

输出：签名 (r, s)——与普通 ECDSA 签名完全相同
```

### ECDSA TSS 的主要协议

| 协议 | 年份 | 轮数 | 特点 |
|------|------|------|------|
| GG18 | 2018 | 多轮 | 第一个实用的门限 ECDSA |
| GG20 | 2020 | 优化 | 改进了 GG18 的效率 |
| CGGMP | 2021 | 优化 | 更强的安全证明 |
| DKLs | 2018 | 2 轮 | 两方场景优化 |

### Schnorr/EdDSA 的 TSS（更简单）

Schnorr 签名的线性性使得门限签名自然得多：

```
Schnorr 签名：s = k + e × d

门限版本（2/2）：
- P₁ 持有 d₁, k₁
- P₂ 持有 d₂, k₂
- d = d₁ + d₂, k = k₁ + k₂

签名：
1. R = k₁ × G + k₂ × G = k × G
2. e = Hash(R || Q || m)
3. s₁ = k₁ + e × d₁（P₁ 本地计算）
4. s₂ = k₂ + e × d₂（P₂ 本地计算）
5. s = s₁ + s₂

不需要复杂的 MPC 乘法协议！
```

这就是为什么 Schnorr/EdDSA 被认为更"MPC 友好"。

### 阶段三：密钥刷新（Proactive Security）

```
目标：更新所有分片，使旧分片失效，但公钥不变

方法：
1. 各方共同生成一个"零值"的秘密分享
   即：分片 δ₁, δ₂, δ₃ 满足 δ₁ + δ₂ + δ₃ = 0

2. 每方将自己的分片加上对应的 δ：
   s₁' = s₁ + δ₁
   s₂' = s₂ + δ₂
   s₃' = s₃ + δ₃

3. 新分片 s₁', s₂', s₃' 仍然是同一个私钥的有效分享
   因为 s₁' + s₂' + s₃' = (s₁+s₂+s₃) + (δ₁+δ₂+δ₃) = d + 0 = d

4. 旧分片 s₁, s₂, s₃ 与新分片不兼容，即使泄露也无法使用
```

安全意义：
- 即使攻击者在不同时间窗口获取了不同方的分片，也无法组合使用
- 定期刷新可以"治愈"部分泄露

## 工程实现的挑战

### 通信复杂度

| 协议阶段 | 通信轮数 | 消息量 |
|---------|---------|--------|
| DKG | O(n²) 消息 | 每方发送给其他所有方 |
| 签名（GG20） | 多轮 | 依赖参与方数量 |
| 签名（FROST/Schnorr） | 2 轮 | 更高效 |
| 密钥刷新 | O(n²) 消息 | 类似 DKG |

### 活性问题

MPC 签名需要多方同时在线并响应。如果某方离线：
- 签名无法完成
- 需要等待或使用其他分片组合

解决方案：
- 预签名（Pre-signing）：提前生成签名的中间状态
- 异步协议：减少对同时在线的要求
- 冗余分片：n > t，允许部分方离线

### 恶意参与方

协议需要处理参与方可能作弊的情况：
- 发送错误的分片
- 不遵循协议步骤
- 试图从交互中提取其他方的信息

防御机制：
- 零知识证明（ZKP）：证明计算正确而不暴露输入
- 可验证秘密分享（VSS）：验证分片的正确性
- 中止机制：检测到作弊时安全终止

### 性能

典型的 TSS 签名延迟：

| 场景 | 延迟 |
|------|------|
| 2/2 本地（同一设备） | ~100ms |
| 2/3 局域网 | ~200-500ms |
| 2/3 跨地域 | ~500ms-2s |
| 3/5 跨地域 | ~1-5s |

对比：本地 ECDSA 签名 < 1ms

## MPC 钱包的架构模式

### 模式一：客户端-服务器（2/2）

```
┌─────────────┐              ┌─────────────┐
│  用户设备    │    TLS/WSS   │   MPC 服务器 │
│             │ ←──────────→ │             │
│  分片 A     │   签名协议    │  分片 B     │
│  本地存储    │              │  HSM 存储   │
└─────────────┘              └─────────────┘
```

代表：Zengo、Particle Network

### 模式二：三方分片（2/3）

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  用户设备    │   │  MPC 服务器  │   │  备份存储    │
│  分片 A     │   │  分片 B     │   │  分片 C     │
└─────────────┘   └─────────────┘   └─────────────┘
      │                  │                  │
      └────── 任意两方协作签名 ──────────────┘
```

代表：Web3Auth、Fireblocks（机构版）

### 模式三：去中心化 MPC 网络

```
┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐
│节点1 │ │节点2 │ │节点3 │ │节点4 │ │节点5 │
└─────┘ └─────┘ └─────┘ └─────┘ └─────┘
   │       │       │       │       │
   └───────┴───────┴───────┴───────┘
          去中心化签名网络
          门限：3/5
```

代表：Lit Protocol、NEAR Chain Signatures

## MPC vs 其他方案的技术对比

| 维度 | MPC/TSS | 多签合约 | 硬件钱包 | 单密钥 |
|------|---------|---------|---------|--------|
| 密钥存在形态 | 分片，从不完整 | 多个独立完整密钥 | 一个完整密钥（隔离） | 一个完整密钥 |
| 链上可见性 | 不可见（普通签名） | 可见（合约调用） | 不可见 | 不可见 |
| 链兼容性 | 任何链 | 需要智能合约 | 任何链 | 任何链 |
| 恢复机制 | 分片重组 | 合约逻辑 | 助记词 | 助记词 |
| 升级灵活性 | 可刷新分片 | 可升级合约 | 固件更新 | 无 |
| 单点故障 | 无（门限） | 无（多签） | 有（设备） | 有（密钥） |
| 延迟 | 较高（多轮通信） | 较高（链上确认） | 低（本地签名） | 最低 |

## 小结

MPC/TSS 是密码学在钱包安全领域的前沿应用。它的核心价值是消除单点故障——让"一个秘密被一个人完整持有"这个风险模型不再存在。

但 MPC 不是免费的午餐：它引入了通信复杂度、活性依赖、实现难度等新的挑战。在实际产品中，MPC 通常与其他安全机制（硬件安全模块、访问控制、审计日志）组合使用，构成完整的安全体系。

理解 MPC 的技术原理，才能正确评估各种"MPC 钱包"的安全声明——不是所有声称使用 MPC 的产品都有同等的安全性。
