# 供应链攻击：恶意依赖与构建劫持

## 一句话总结

钱包的安全不只是钱包本身的代码——它依赖的每一个第三方库、每一个 npm 包、每一个 CI/CD 步骤，都是潜在的攻击面。

## 什么是供应链攻击

```
传统攻击：直接攻击目标系统
供应链攻击：通过攻击软件供应链中的环节

类比：
- 直接抢银行 → 攻击银行的保安系统
- 供应链攻击 → 攻击运钞车、贿赂员工、篡改 ATM 厂商

加密钱包的供应链：
- 第三方 npm 包
- 编译工具链
- CI/CD 系统
- 代码签名证书
- 应用商店分发
- 硬件供应链（硬件钱包）
- 用户系统环境
```

## 主要攻击类型

### 攻击一：恶意 npm 包

```
攻击方式：
1. 发布看起来正常的 npm 包（或劫持现有包）
2. 包中插入恶意代码
3. 钱包项目（间接）依赖了这个包
4. 用户安装钱包时引入恶意代码

触发条件：
- 通常在 postinstall 脚本中
- 或在被调用的函数中
- 在特定条件下激活

代表案例：
- event-stream 事件（2018）：
  - 流行的 npm 包 event-stream
  - 维护者把维护权转给一个新人
  - 新人是攻击者
  - 加入了窃取 Copay 钱包私钥的代码
  - 影响范围广

- ua-parser-js 事件（2021）：
  - 数百万下载的库被劫持
  - 加入挖矿代码和密码窃取器
```

### 攻击二：依赖混淆

```
攻击方式：
1. 内部包名 + 公共仓库
   公司用 @company/internal-package
   公共 npm 也有同名包但版本号更高
2. 包管理器自动选择高版本（公共的恶意版本）
3. 内部代码中执行恶意逻辑

代表案例：
- Alex Birsan 的研究（2021）：
  - 演示了对 Apple、Microsoft、Tesla 等的攻击
  - 通过依赖混淆获得代码执行权限
```

### 攻击三：劫持账号

```
攻击方式：
1. 攻击维护者的 npm/GitHub 账号
2. 直接修改包代码
3. 发布新版本
4. 用户更新时引入恶意代码

技术手段：
- 钓鱼维护者
- 凭据填充攻击
- 攻击 2FA（如 SIM 交换）
- 维护者电脑被黑

防御困难：
- 维护者本身就是受害者
- 难以检测
- 等发现时已经晚了
```

### 攻击四：构建系统污染

```
攻击方式：
1. 攻击 CI/CD 系统（如 GitHub Actions、Jenkins）
2. 在构建过程中注入恶意代码
3. 编译产物被污染
4. 但源代码看起来正常

代表案例：
- SolarWinds 事件（2020）：
  - 攻击者入侵构建系统
  - 在编译时注入后门
  - 影响数千客户
  - 但源代码是干净的（很难发现）

- Codecov 事件（2021）：
  - Bash uploader 被篡改
  - 窃取 CI 环境变量（API key 等）
  - 间接影响许多项目
```

### 攻击五：代码签名证书泄露

```
攻击方式：
1. 攻击者获得开发商的代码签名证书
2. 签发恶意软件
3. 用户系统认为是合法软件
4. 安装并执行

后果：
- 绕过浏览器/系统的安全检查
- 用户难以分辨
- 影响范围大
```

### 攻击六：硬件供应链

```
针对硬件钱包：
1. 在生产过程中植入后门芯片
2. 运输过程中替换设备
3. 在销售环节篡改

经典案例：
- 二手 Trezor 被预装恶意固件
- 用户使用后助记词被窃取

防御：
- 只从官方渠道购买
- 检查包装完整性
- 首次使用时验证设备真实性
```

## 钱包行业的真实案例

### Ledger Connect Kit 事件（2023.12）

```
事件经过：
1. Ledger Connect Kit（前端 SDK）的 npm 包被劫持
2. 攻击者入侵了 Ledger 前员工的 npm 账户
3. 发布恶意版本，加入钱包窃取代码
4. 多个 DApp（包括 Sushi、Zapper 等）使用了这个 SDK
5. 用户访问这些 DApp 时，恶意代码被加载
6. 用户签名时被诱导转账给攻击者

影响：
- 持续约 5 小时
- 损失约 $610K
- 影响多个主流 DApp
- 引发对前端 SDK 安全的大讨论

教训：
- 依赖锁定的重要性
- 前端代码的安全审计
- SDK 提供商的责任
```

### 2024 年 Solana 钱包事件

```
2024 年初：
- 多个 Solana 钱包用户报告资产被盗
- 调查发现是某个 npm 包被污染
- 攻击者通过供应链攻击影响多个钱包

具体细节：
- 攻击者发布了与流行 Solana 库类似名字的包
- 一些钱包项目误用了这个包
- 包中包含窃取私钥的代码

影响：
- 损失估计数百万美元
- 多个钱包项目紧急修复
- 推动行业加强供应链安全
```

## 钱包的防御措施

### 防御一：依赖管理

```
最佳实践：

1. 严格依赖锁定
   - 使用 package-lock.json / yarn.lock
   - 不允许浮动版本（如 ^1.0.0）
   - 定期审查依赖更新

2. 最小化依赖
   - 不要为小功能引入大库
   - 评估每个依赖的必要性
   - 减少传递依赖

3. 依赖审计
   - 定期运行 npm audit
   - 使用 Snyk、Dependabot 等工具
   - 对重要依赖做代码审查

4. 依赖来源控制
   - 使用私有 npm 镜像（如 Verdaccio）
   - 缓存已审核的版本
   - 减少对公共 npm 的实时依赖
```

### 防御二：构建安全

```
最佳实践：

1. 可重现构建
   - 相同源码 → 相同二进制
   - 用户可以验证构建
   - Bitcoin、Tor 等都做了这个

2. 隔离的构建环境
   - 每次构建用干净环境
   - 限制构建机器的网络访问
   - 不在构建机器存储敏感凭据

3. 代码签名
   - 多人签名（不是一个人能发布）
   - 硬件签名设备
   - 签名前的代码审查

4. 透明日志
   - 所有发布记录在公开日志
   - 用户可以验证版本来源
```

### 防御三：运行时保护

```
最佳实践：

1. 子资源完整性（SRI）
   - <script integrity="sha384-...">
   - 浏览器验证脚本未被篡改

2. CSP（内容安全策略）
   - 限制可以加载的资源
   - 防止 XSS 注入
   - 限制外部 API 调用

3. 沙箱化
   - 第三方代码在沙箱中运行
   - 限制访问敏感数据
   - MetaMask Snaps 是例子

4. 运行时检测
   - 检测异常行为
   - 异常网络请求告警
   - 异常签名请求拦截
```

### 防御四：硬件钱包的特殊防御

```
最佳实践：

1. 安全启动
   - 验证固件签名
   - 拒绝未签名的固件
   - 防止恶意固件运行

2. 防篡改包装
   - 物理封条
   - 撕开标记不可恢复
   - 用户检查后才使用

3. 设备认证
   - 设备有唯一标识
   - 钱包应用验证设备真实性
   - 拒绝未知/未认证设备

4. 用户验证步骤
   - 首次使用要确认设备
   - 显示设备特定信息（如指纹）
   - 与官方提供的特征对比
```

## 用户层面的防御

### 用户能做什么

```
1. 只从官方渠道下载
   - 官网下载页（不要点搜索引擎广告）
   - 应用商店（注意伪造）
   - 浏览器扩展商店（注意伪造）

2. 验证下载内容
   - 检查文件哈希
   - 检查代码签名
   - 与社区反馈对比

3. 谨慎更新
   - 不要立即更新（让别人先验证）
   - 重要更新看社区反馈
   - 异常情况立即询问

4. 多重验证
   - 交易在硬件钱包屏幕上验证
   - 不完全信任前端显示
   - 转账金额、地址都要看清
```

### 减少攻击面

```
1. 用专门的设备做加密操作
   - 不在日常电脑上做
   - 减少其他软件干扰
   - 减少恶意软件机会

2. 用专门的浏览器
   - 不安装其他扩展
   - 不访问其他网站
   - 隔离风险

3. 大额用硬件钱包
   - 即使前端被污染
   - 硬件钱包屏幕显示真实交易
   - 用户可以拒绝异常交易
```

## 行业协作

### 信息共享

```
社区机制：
- 漏洞披露平台（如 Code4rena、Immunefi）
- 安全公告共享
- 钓鱼/恶意包数据库
- 实时威胁情报
```

### 标准化

```
正在发展的标准：
- SBOM（软件物料清单）：列出所有依赖
- SLSA（供应链层级）：构建过程的安全级别
- in-toto：端到端的供应链验证
```

## 小结

供应链攻击是钱包安全最隐蔽也最难防御的威胁之一。它的特点：
- **隐蔽**：攻击不在表面，难以发现
- **范围广**：一次攻击影响多个项目
- **后果严重**：直接窃取资产
- **防御难**：需要全链路安全

钱包项目的责任：
1. 严格的依赖管理
2. 安全的构建流程
3. 运行时保护机制
4. 持续的安全审计

但完全防御供应链攻击是不可能的——攻击面太大。所以也需要：
- 用户的谨慎
- 社区的监督
- 快速的响应能力
- 损失的应急方案

随着钱包行业的成熟，供应链安全会从"被忽视"变成"必修课"。
