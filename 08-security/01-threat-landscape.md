# 钱包安全威胁全景：攻击面分类

## 一句话总结

钱包的攻击面远比大多数人想象的广——从密码学层面的密钥提取到社会工程层面的钓鱼欺骗，攻击者会利用任何薄弱环节。

## 攻击面分层模型

```
┌─────────────────────────────────────────────────────────┐
│  Layer 5: 社会工程层                                     │
│  钓鱼网站 | 假客服 | 社交媒体诈骗 | 虚假空投             │
├─────────────────────────────────────────────────────────┤
│  Layer 4: 应用层                                         │
│  恶意 DApp | 恶意签名请求 | 前端劫持 | 恶意浏览器扩展    │
├─────────────────────────────────────────────────────────┤
│  Layer 3: 钱包软件层                                     │
│  代码漏洞 | 供应链攻击 | 内存泄露 | 不安全的存储          │
├─────────────────────────────────────────────────────────┤
│  Layer 2: 系统/设备层                                    │
│  恶意软件 | Root/越狱 | 剪贴板劫持 | 屏幕录制            │
├─────────────────────────────────────────────────────────┤
│  Layer 1: 密码学/协议层                                  │
│  弱随机数 | 签名漏洞 | 重放攻击 | 协议缺陷               │
└─────────────────────────────────────────────────────────┘

攻击频率：Layer 5 >> Layer 4 > Layer 3 > Layer 2 >> Layer 1
攻击难度：Layer 1 >> Layer 2 > Layer 3 > Layer 4 >> Layer 5
```

## Layer 5：社会工程攻击（最常见）

### 钓鱼网站

```
攻击流程：
1. 创建与正规 DApp 几乎一模一样的假网站
2. 通过 Google 广告、社交媒体、假空投推广
3. 用户访问假网站，连接钱包
4. 假网站请求恶意签名（Approve 无限额度、Permit 签名等）
5. 用户在钱包中确认（因为看不懂签名内容）
6. 攻击者用获得的授权转走用户资产

常见手法：
- 域名相似：uniswap.org → un1swap.org / uniswap.com
- 假空投：claim-airdrop.xyz
- 假 Mint：bayc-mint.com
- 搜索引擎广告：搜索 "Uniswap" 第一个结果是钓鱼广告
```

### 地址投毒（Address Poisoning）

```
攻击流程：
1. 攻击者监控目标地址的交易
2. 生成一个与目标常用地址首尾几位相同的地址
   真实地址：0xAbC...789
   伪造地址：0xAbC...789（中间不同）
3. 从伪造地址向目标发送 0 金额交易
4. 目标在交易历史中看到这个"熟悉"的地址
5. 下次转账时从历史记录复制了伪造地址
6. 资产转到攻击者地址

防御：
- 完整显示地址（不要只显示首尾）
- 地址簿功能（从地址簿选择而非复制）
- 标记可疑的 0 金额转入
- 首次转账警告
```

### 假客服/假官方

```
场景：
- 用户在 Discord/Telegram 求助
- "官方客服"主动私信
- 要求用户提供助记词"验证身份"
- 或引导用户访问"修复工具"网站

防御：
- 教育用户：官方永远不会要求助记词
- 钱包内置帮助系统（减少用户去外部求助）
```

## Layer 4：应用层攻击

### 恶意签名请求

```
类型 1：Approve 无限额度
- DApp 请求 approve(spender, type(uint256).max)
- 用户确认后，spender 可以随时转走所有代币
- 即使用户之后不再使用该 DApp，授权仍然有效

类型 2：Permit 签名（EIP-2612）
- 链下签名，不需要 Gas
- 用户可能不知道自己在"授权"
- 签名后攻击者可以在链上执行 permit + transferFrom

类型 3：eth_sign（盲签）
- 签名任意数据，用户完全看不懂内容
- 可能是交易、可能是授权、可能是任何东西
- 很多钱包已经禁用或警告 eth_sign

类型 4：setApprovalForAll
- 一次性授权某地址转移你所有的 NFT
- 常见于 NFT 市场（合法用途）
- 也被钓鱼网站滥用
```

### 前端劫持

```
攻击流程：
1. 攻击者入侵正规 DApp 的前端（DNS 劫持、CDN 投毒）
2. 修改前端代码，将交易目标地址替换为攻击者地址
3. 用户访问的是正确的域名，但前端已被篡改
4. 用户正常操作，但资金流向攻击者

案例：
- 2022 年 BadgerDAO 前端被黑，损失 $120M
- 多个 DeFi 协议的 DNS 被劫持

防御：
- 交易模拟（检查资金流向）
- 合约地址白名单
- 前端完整性验证（SRI）
```

### 恶意浏览器扩展

```
攻击方式：
- 伪装成有用工具（翻译、截图、广告拦截）
- 请求"读取所有网站数据"权限
- 注入恶意脚本到 DApp 页面
- 修改交易参数（替换接收地址）
- 或直接读取钱包扩展的存储

防御：
- 最小化安装的扩展
- 使用独立的浏览器 Profile 进行加密操作
- 钱包检测异常的 Provider 注入
```

## Layer 3：钱包软件层攻击

### 供应链攻击

```
攻击向量：
1. 恶意 npm 包：钱包依赖的某个库被植入后门
2. 构建环境污染：CI/CD 被入侵，构建产物被篡改
3. 更新劫持：钱包更新包被替换为恶意版本

案例：
- event-stream 事件（2018）：流行 npm 包被植入窃取比特币的代码
- Ledger Connect Kit 事件（2023）：Ledger 的前端库被注入恶意代码

防御：
- 依赖锁定（lock file）
- 依赖审计
- 可重现构建（Reproducible Build）
- 代码签名验证
```

### 内存攻击

```
攻击场景：
- 私钥解密后存在于内存中
- 恶意软件扫描进程内存
- 找到私钥格式的数据
- 提取并使用

防御：
- 最小化私钥在内存中的时间
- 使用后立即清零
- 安全内存分配（mlock）
- 硬件安全模块（密钥不进入主内存）
```

## Layer 2：系统/设备层攻击

### 剪贴板劫持

```
攻击流程：
1. 恶意软件监控剪贴板
2. 检测到加密地址格式的内容
3. 替换为攻击者的地址
4. 用户粘贴时使用的是攻击者地址

防御：
- 钱包内置地址簿（不需要复制粘贴）
- 粘贴后显示完整地址供确认
- 与上次使用的地址对比
```

### 恶意软件/键盘记录

```
攻击方式：
- 记录用户输入的密码/助记词
- 截屏/录屏捕获敏感信息
- 读取钱包的加密存储文件（配合密码）

防御：
- 生物识别替代密码输入
- 安全键盘（防截屏）
- 设备安全检测（Root/越狱检测）
```

## Layer 1：密码学/协议层攻击

### 弱随机数

```
如果签名时的随机数 k 有缺陷：
- 两次签名使用相同的 k → 私钥可直接计算
- k 有偏差 → 通过多个签名统计分析恢复私钥

历史案例：
- 2013 年 Android SecureRandom 漏洞导致比特币被盗
- PlayStation 3 的 ECDSA 实现使用固定 k，私钥被提取

防御：
- 使用 RFC 6979（确定性签名）
- 使用经过审计的密码学库
- 不自己实现密码学
```

### 重放攻击

```
场景：
- 用户在 Ethereum 上签名了一笔交易
- 攻击者在另一条 EVM 链上重放这笔交易
- 如果没有 Chain ID 保护，交易可能在其他链上也有效

防御：
- EIP-155：交易包含 Chain ID
- EIP-712：签名消息包含域分隔符（chain ID + 合约地址）
```

## 攻击损失统计

### 按攻击类型（2023-2024 估计）

| 攻击类型 | 年损失估计 | 占比 |
|---------|-----------|------|
| 钓鱼/社会工程 | $500M+ | 40% |
| 协议漏洞（非钱包） | $400M+ | 30% |
| 私钥泄露/管理不善 | $200M+ | 15% |
| 前端/供应链攻击 | $100M+ | 10% |
| 其他 | $50M+ | 5% |

### 关键洞察

```
1. 最大的威胁不是技术攻击，而是社会工程
2. 用户是最薄弱的环节
3. 钱包能做的最有价值的事是帮助用户"不犯错"
4. 技术安全是必要条件，但不是充分条件
```

## 防御体系设计

### 纵深防御原则

```
第一道防线：预防
- 教育用户
- 风险提示
- 默认安全设置

第二道防线：检测
- 交易模拟
- 恶意地址检测
- 异常行为识别

第三道防线：响应
- 授权撤销工具
- 紧急转移
- 事件通知

第四道防线：恢复
- 社交恢复
- 保险机制
- 资产追踪
```

## 小结

钱包安全不是一个单一问题，而是一个多层次的防御体系。关键认知：

1. **最常见的攻击是最低技术含量的**（钓鱼 > 技术攻击）
2. **用户是最大的攻击面**（教育和 UX 比技术更重要）
3. **没有银弹**（需要多层防御的组合）
4. **安全是持续的过程**（攻击手法不断演进）

对钱包产品来说，最大的安全价值不在于"让钱包不被黑"（这是基本要求），而在于"帮助用户不被骗"——通过更好的信息展示、更智能的风险提示、更清晰的操作确认，让用户在面对攻击时能做出正确的判断。
