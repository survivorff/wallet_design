# Onboarding 设计：从 12 个单词到一键创建

## 一句话总结

钱包的 Onboarding 是整个 Web3 用户漏斗中流失最严重的环节——如何在不牺牲安全性的前提下让用户"进来"，是钱包产品最核心的设计挑战。

## 传统 Onboarding 的问题

### 经典流程（MetaMask 式）

```
1. 安装插件/App
2. 创建密码
3. 生成 12 个助记词
4. 要求用户抄写助记词
5. 验证用户确实抄写了（选词确认）
6. 完成，显示空钱包
```

### 每一步的流失

| 步骤 | 流失原因 | 估计流失率 |
|------|---------|-----------|
| 安装 | 不知道装哪个、怕装错 | 30-50% |
| 创建密码 | 又一个密码要记 | 5-10% |
| 助记词展示 | "这是什么？""为什么要抄？" | 20-30% |
| 抄写助记词 | 麻烦、没有笔和纸、不理解重要性 | 30-40% |
| 验证助记词 | 选错了、烦了、放弃 | 10-20% |
| 空钱包 | "然后呢？""怎么买币？" | 高 |

从"想试试 Web3"到"成功创建钱包并完成第一笔操作"，传统流程的转化率可能低于 20%。

### 认知负担分析

新用户在 Onboarding 过程中需要理解的新概念：

```
- 什么是钱包（不是银行账户）
- 什么是助记词（不是密码）
- 为什么要自己保管（没有"找回密码"）
- 什么是地址（不是用户名）
- 什么是网络/链（为什么有这么多）
- 什么是 Gas（为什么转账要手续费）
- 什么是 ETH（为什么需要它才能操作）
```

这些概念对 Web2 用户来说完全陌生，一次性灌输会导致认知过载。

## 现代 Onboarding 方案

### 方案一：社交登录（Social Login）

```
流程：
1. 点击"用 Google 登录"
2. 完成 OAuth 授权
3. 钱包自动创建（MPC 或合约钱包）
4. 用户直接进入 App

技术实现：
- Web3Auth/Torus：社交登录 → 分布式密钥生成
- Privy：社交登录 → 嵌入式钱包
- Magic：邮箱/手机 → 委托密钥管理
```

**优势**：
- 零认知门槛（用户已经会用 Google 登录）
- 秒级完成
- 不需要理解助记词

**代价**：
- 依赖第三方服务（Google、MPC 服务商）
- 用户不"真正"拥有密钥（至少不是传统意义上的）
- 恢复依赖社交账号的安全性

### 方案二：Passkey（WebAuthn）

```
流程：
1. 点击"创建钱包"
2. 系统弹出生物识别（Face ID / 指纹）
3. Passkey 创建完成
4. 钱包地址生成（合约钱包，用 Passkey 作为签名者）

技术实现：
- 浏览器调用 WebAuthn API
- 生成 P-256 密钥对，私钥存储在设备安全芯片中
- 合约钱包验证 P-256 签名（需要 AA 支持）
```

**优势**：
- 用户体验极佳（就像解锁手机）
- 安全性高（硬件级密钥保护）
- 跨设备同步（iCloud Keychain / Google Password Manager）
- 不需要记忆任何东西

**代价**：
- 需要 AA 基础设施（合约钱包 + Paymaster）
- 跨平台兼容性仍有问题
- 恢复依赖平台（Apple/Google）的 Passkey 同步

**代表**：Coinbase Smart Wallet、Clave

### 方案三：渐进式 Onboarding

```
阶段 1（即时）：
- 社交登录或 Passkey 创建钱包
- 用户立即可以使用基础功能
- 不提及助记词、私钥等概念

阶段 2（使用一段时间后）：
- 引导用户设置备份（社交恢复、云备份）
- 逐步介绍安全概念
- 提供升级到自托管的选项

阶段 3（高级用户）：
- 导出私钥/助记词
- 连接硬件钱包
- 设置多签/高级安全策略
```

**核心理念**：不要在用户还没有资产的时候就要求他们理解复杂的安全概念。安全教育应该随着用户资产的增长而渐进。

### 方案四：嵌入式钱包（用户无感）

```
流程：
1. 用户注册某个 App（游戏、社交、NFT 平台）
2. App 后台自动为用户创建钱包
3. 用户完全不知道自己"有一个钱包"
4. 链上操作对用户透明

技术实现：
- App 集成 Privy/Dynamic/Particle SDK
- 钱包创建在后台完成
- 签名由 SDK 处理（可能结合 MPC）
- Gas 由 App 赞助（Paymaster）
```

**优势**：
- 零 Onboarding 摩擦
- 用户不需要任何 Web3 知识
- 适合 Web2 → Web3 的过渡

**代价**：
- 用户不"拥有"自己的钱包（至少初始状态）
- 去中心化程度最低
- 用户可能不知道自己的资产在链上

## Onboarding 设计原则

### 原则一：延迟复杂性

```
❌ 错误：一开始就要求用户理解所有概念
✅ 正确：只在用户需要时才引入新概念

示例：
- 不要在创建钱包时解释 Gas → 在第一次交易时解释
- 不要在创建时要求备份 → 在有了一定资产后提醒
- 不要在创建时选择网络 → 自动检测或默认选择
```

### 原则二：熟悉的模式

```
❌ 错误：发明全新的交互模式
✅ 正确：复用用户已经熟悉的模式

示例：
- 用"登录"代替"连接钱包"
- 用"账户"代替"地址"
- 用"确认支付"代替"签名交易"
- 用"备份"代替"导出助记词"
```

### 原则三：即时价值

```
❌ 错误：创建完钱包后显示空白页面
✅ 正确：创建完立即引导用户完成第一个有价值的操作

示例：
- 领取一个免费 NFT
- 完成一笔小额 Swap
- 加入一个社区
- 领取空投/奖励
```

### 原则四：安全渐进

```
安全措施应该与资产规模匹配：

$0-$100：社交登录 + 云备份就够了
$100-$1000：建议设置社交恢复
$1000-$10000：强烈建议导出助记词或连接硬件钱包
$10000+：推荐多签或硬件钱包
```

## 不同产品的 Onboarding 对比

| 产品 | 方式 | 时间 | 需要理解的概念 |
|------|------|------|--------------|
| MetaMask | 助记词 | 3-5 分钟 | 助记词、密码、网络 |
| Coinbase Smart Wallet | Passkey | 10 秒 | 无 |
| Phantom | 助记词（可跳过） | 1-3 分钟 | 助记词（可选） |
| Privy 集成的 App | 社交登录 | 5 秒 | 无 |
| OKX Wallet | 助记词/社交 | 1-3 分钟 | 取决于选择 |
| Argent | 邮箱 + 监护人 | 2 分钟 | 监护人概念 |

## 衡量 Onboarding 成功的指标

| 指标 | 定义 | 目标 |
|------|------|------|
| 完成率 | 开始创建 → 成功创建的比例 | >80% |
| 完成时间 | 从开始到完成的时间 | <60 秒 |
| 首次操作率 | 创建后 24h 内完成第一笔操作 | >50% |
| 7 日留存 | 创建后第 7 天仍活跃 | >30% |
| 备份率 | 完成安全备份的用户比例 | >60%（渐进式） |

## 小结

Onboarding 设计的本质是一个权衡：**安全教育的完整性 vs 用户进入的摩擦**。

传统方案（助记词）把所有安全责任一次性推给用户，导致大量流失。现代方案（社交登录、Passkey、嵌入式）选择先让用户进来，再逐步建立安全意识。

没有完美的方案，但方向是清晰的：**让进入 Web3 像注册一个普通 App 一样简单，同时保留用户在需要时升级到完全自托管的路径**。
