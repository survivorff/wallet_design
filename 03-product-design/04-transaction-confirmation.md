# 交易确认页设计：如何让用户"看懂"自己在签什么

## 一句话总结

交易确认页是钱包安全的最后一道防线——如果用户看不懂自己在签什么，再好的密钥管理也无法防止用户主动签署恶意交易。

## 问题的严重性

### 大多数钓鱼攻击的本质

```
攻击流程：
1. 用户访问钓鱼网站（看起来像正规 DApp）
2. 网站请求用户签名
3. 钱包弹出确认页
4. 用户看不懂内容，但"信任"这个网站
5. 用户点击确认
6. 资产被盗

关键点：攻击成功不是因为钱包被黑，而是因为用户"自愿"签署了恶意交易
```

### 用户为什么看不懂

传统钱包（如早期 MetaMask）的确认页展示：

```
┌─────────────────────────────────┐
│  确认交易                        │
│                                  │
│  To: 0x7a250d5630B4cF539739dF2C │
│      5dAcb4c659F2488D            │
│                                  │
│  Data: 0x7ff36ab500000000000000  │
│  000000000000000000000000000000  │
│  0000000000000000de0b6b3a764000  │
│  00...                           │
│                                  │
│  Value: 1.0 ETH                  │
│  Gas: 0.005 ETH                  │
│                                  │
│  [拒绝]          [确认]          │
└─────────────────────────────────┘
```

用户能从中获得的信息：几乎为零。

## 交易解析（Transaction Decoding）

### 基本解析

将原始 calldata 解码为人类可读的函数调用：

```
原始数据：
0x7ff36ab5000000000000000000000000000000000000000000000000000000...

解析后：
函数：swapExactETHForTokens
参数：
  - amountOutMin: 1,950 USDC
  - path: [WETH → USDC]
  - to: 0xYourAddress
  - deadline: 2024-01-15 12:00:00
```

实现方式：
- ABI 解码：如果有合约 ABI，直接解码
- 4bytes 数据库：通过函数选择器（前 4 字节）查询已知函数签名
- 合约验证：从 Etherscan 等获取已验证合约的 ABI

### 语义化展示

比函数名更进一步，用自然语言描述操作的含义：

```
┌─────────────────────────────────┐
│  🔄 Swap 交易                    │
│                                  │
│  你将支付：1.0 ETH (~$2,000)    │
│  你将收到：≥1,950 USDC          │
│  滑点保护：2.5%                  │
│                                  │
│  通过：Uniswap V3               │
│  路径：ETH → USDC               │
│  截止时间：15 分钟后             │
│                                  │
│  网络费用：~$3.50                │
│                                  │
│  [拒绝]          [确认]          │
└─────────────────────────────────┘
```

### 交易模拟（Transaction Simulation）

最强大的方案：在确认前模拟执行交易，展示实际结果。

```
┌─────────────────────────────────┐
│  📊 交易模拟结果                  │
│                                  │
│  资产变化预览：                   │
│  - ETH:  -1.0 ($2,000)          │
│  + USDC: +1,985 ($1,985)        │
│  - Gas:  -0.003 ETH ($6)        │
│                                  │
│  授权变化：无                     │
│                                  │
│  ✅ 模拟成功                      │
│                                  │
│  [拒绝]          [确认]          │
└─────────────────────────────────┘
```

代表产品：
- **Rabby**：内置交易预执行，显示资产变化
- **Blowfish**：交易模拟 API，被多个钱包集成
- **Pocket Universe**：浏览器插件，拦截并模拟交易
- **Fire**：交易模拟和风险评估

## 不同类型交易的确认页设计

### 1. 简单转账

```
┌─────────────────────────────────┐
│  💸 转账                         │
│                                  │
│  发送：1.5 ETH (~$3,000)        │
│  接收方：vitalik.eth             │
│          0xd8dA...6045           │
│                                  │
│  ⚠️ 首次向此地址转账              │
│                                  │
│  网络费用：~$1.20                │
│  [拒绝]          [确认]          │
└─────────────────────────────────┘
```

关键设计点：
- 显示 ENS 名称（如果有）
- 标记是否首次向该地址转账
- 大额转账额外警告

### 2. 代币授权（Approve）

```
┌─────────────────────────────────┐
│  🔓 代币授权                     │
│                                  │
│  授权对象：Uniswap V3 Router     │
│           0x68b3...4a1e          │
│  授权代币：USDC                  │
│  授权额度：无限 ⚠️               │
│                                  │
│  ⚠️ 风险提示：                    │
│  无限授权意味着该合约可以随时     │
│  转走你所有的 USDC               │
│                                  │
│  [拒绝] [授权精确金额] [确认]    │
└─────────────────────────────────┘
```

关键设计点：
- 明确标注"无限授权"的风险
- 提供"授权精确金额"的替代选项
- 显示合约是否经过验证

### 3. NFT 相关操作

```
┌─────────────────────────────────┐
│  🖼️ NFT 操作                    │
│                                  │
│  操作：setApprovalForAll         │
│  集合：Bored Ape Yacht Club     │
│  授权给：OpenSea Seaport        │
│                                  │
│  ⚠️ 这将授权该合约转移你在       │
│  此集合中的所有 NFT              │
│                                  │
│  你持有的 NFT：                   │
│  - BAYC #1234 (Floor: 30 ETH)  │
│  - BAYC #5678 (Floor: 30 ETH)  │
│  总价值：~$120,000              │
│                                  │
│  [拒绝]          [确认]          │
└─────────────────────────────────┘
```

### 4. 签名消息（EIP-712）

```
┌─────────────────────────────────┐
│  ✍️ 签名请求                     │
│                                  │
│  类型：Permit（链下授权）         │
│                                  │
│  你正在签署：                     │
│  允许 0x1234...abcd              │
│  花费你的 10,000 USDC            │
│  有效期至：2024-12-31            │
│                                  │
│  ⚠️ 注意：这是一个 Permit 签名   │
│  签署后对方可以无需你再次确认     │
│  即转走你的代币                   │
│                                  │
│  [拒绝]          [签名]          │
└─────────────────────────────────┘
```

关键设计点：
- Permit 签名特别危险（链下签名，链上执行）
- 必须明确告知用户签名的后果
- 显示授权的具体金额和有效期

## 风险提示系统

### 风险等级

```
🟢 低风险：已知安全合约、常规操作
🟡 中风险：首次交互的合约、大额操作
🔴 高风险：可疑合约、异常授权、已知钓鱼地址
⛔ 极高风险：确认的恶意合约、黑名单地址
```

### 风险信号

| 信号 | 风险等级 | 说明 |
|------|---------|------|
| 合约未验证 | 🟡 | 无法确认代码内容 |
| 合约刚部署 | 🟡 | 可能是临时钓鱼合约 |
| 无限授权 | 🟡 | 过度授权风险 |
| 首次交互 | 🟡 | 用户不熟悉的合约 |
| 地址投毒匹配 | 🔴 | 可能是伪造的相似地址 |
| 黑名单地址 | ⛔ | 已知的恶意地址 |
| Permit 签名 | 🟡-🔴 | 链下授权，容易被滥用 |
| 大额转账到新地址 | 🟡 | 可能是误操作 |

### 数据来源

- 链上数据：合约部署时间、交互量、代码验证状态
- 黑名单数据库：已知钓鱼地址、恶意合约
- 社区报告：用户举报的可疑地址
- 模拟结果：交易执行后的状态变化

## 设计原则

### 1. 信息层次化

```
第一层（必看）：操作类型 + 资产变化 + 总费用
第二层（建议看）：合约信息 + 风险提示
第三层（高级）：原始数据 + 技术细节
```

### 2. 对比展示

```
✅ 好的设计：
"你将支付 1 ETH，收到约 1,985 USDC"

❌ 差的设计：
"调用 swapExactETHForTokens，参数：amountOutMin=1950000000..."
```

### 3. 异常突出

正常操作不需要额外关注，异常操作需要强制用户注意：

```
正常：绿色/中性色调，一键确认
异常：红色警告，需要额外确认步骤（如输入"CONFIRM"）
```

### 4. 可操作的建议

```
❌ 只告诉用户"这很危险"
✅ 告诉用户"这很危险，你可以这样做来降低风险"

示例：
"无限授权有风险 → 建议授权精确金额"
"Gas 异常高 → 建议稍后再试"
"首次向此地址转账 → 建议先发送小额测试"
```

## 小结

交易确认页是钱包安全的"最后一公里"。技术上的安全（密钥管理、加密存储）保护的是"钱包不被黑"，而确认页设计保护的是"用户不被骗"。

在当前 Web3 环境下，社会工程攻击（钓鱼）造成的损失远大于技术攻击。因此，一个好的交易确认页设计——清晰的信息展示、准确的风险提示、可操作的安全建议——可能比任何底层安全技术都更能保护用户的资产。
