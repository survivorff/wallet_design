# 以太坊带来的范式转变：从"存币"到"交互"

## 一句话总结

以太坊让钱包从一个"保险箱"变成了一个"遥控器"——你不只是存资产，你要和链上程序交互。

## 比特币钱包 vs 以太坊钱包：根本性差异

### 比特币时代的钱包

在比特币世界里，钱包的核心动作只有两个：
1. **收**：生成地址，等别人转账
2. **发**：构建交易，把币转给别人

钱包就是一个数字保险箱，打开、存入、取出，完事。

### 以太坊改变了什么

2015 年以太坊上线后，钱包需要做的事情爆炸性增长：

| 比特币钱包 | 以太坊钱包 |
|-----------|-----------|
| 收发 BTC | 收发 ETH + 任意 ERC-20 代币 |
| 管理 UTXO | 管理账户状态（余额 + nonce） |
| 签名转账交易 | 签名任意合约调用 |
| — | 授权（Approve）代币给合约 |
| — | 与 DeFi 协议交互 |
| — | 铸造/转移 NFT |
| — | 参与 DAO 投票 |
| — | 部署智能合约 |

### 账户模型的差异

```
比特币：UTXO 模型
┌─────────────────────────────────────┐
│ 你的"余额" = 所有未花费输出的总和     │
│ UTXO_1: 0.5 BTC                     │
│ UTXO_2: 0.3 BTC                     │
│ UTXO_3: 1.2 BTC                     │
│ 总计: 2.0 BTC                       │
└─────────────────────────────────────┘

以太坊：账户模型
┌─────────────────────────────────────┐
│ 地址: 0xAbC...123                    │
│ 余额: 2.0 ETH                       │
│ Nonce: 42（已发送 42 笔交易）         │
│ 代码: 无（EOA 外部账户）              │
│ 存储: 无                             │
└─────────────────────────────────────┘
```

账户模型对钱包的影响：
- 余额直接可读，不需要计算 UTXO 集合
- Nonce 机制意味着交易有严格顺序
- 同一个地址反复使用（隐私性降低，但 UX 更简单）

## 智能合约：钱包的新维度

### 什么变了

在比特币上，交易的含义是确定的：从 A 转 X 个币到 B。

在以太坊上，交易可以是任何事情——因为你调用的是智能合约的任意函数。钱包需要：

1. **理解** 用户要调用什么合约、什么函数
2. **展示** 这笔交易会做什么（交易解析）
3. **估算** 需要多少 Gas
4. **签名** 交易数据（不只是转账金额）
5. **追踪** 交易状态和结果

### 交易数据的复杂性

比特币交易数据（简化）：
```
{
  "from": "1A1zP1...",
  "to": "1BvBMSE...",
  "amount": "1.0 BTC"
}
```

以太坊交易数据（一笔 Uniswap 交换）：
```
{
  "from": "0xUser...",
  "to": "0xUniswapRouter...",
  "value": "1000000000000000000",  // 1 ETH
  "data": "0x7ff36ab5000000000000000000000000000000000000000000000000000000..."
  // ↑ 编码了：函数名 + 最小输出量 + 路径 + 接收地址 + 截止时间
}
```

钱包面临的挑战：如何把这串十六进制数据翻译成用户能理解的信息？

## ERC-20：代币标准改变了资产展示

### 之前

比特币钱包只需要显示一种资产：BTC。

### 之后

以太坊上任何人都可以发行代币，钱包需要：
- 发现用户持有哪些代币（扫描 Transfer 事件）
- 显示代币名称、符号、精度、图标
- 处理代币转账（调用合约的 transfer 函数，而不是直接转 ETH）
- 管理代币授权（approve/allowance 机制）

这直接催生了"资产列表"这个产品概念，以及后来的 Token List 标准。

## Gas 机制：钱包的新负担

以太坊引入了 Gas 概念，给钱包增加了巨大的复杂性：

### 用户需要理解的概念

- Gas Limit：这笔交易最多消耗多少计算单元
- Gas Price（EIP-1559 之前）：每单位 Gas 愿意付多少
- Base Fee + Priority Fee（EIP-1559 之后）：基础费 + 小费
- 交易可能因 Gas 不足而失败（但 Gas 费照扣）

### 钱包需要做的事

- 估算 Gas 用量（调用 eth_estimateGas）
- 建议合理的 Gas Price（查询网络拥堵情况）
- 处理交易卡住的情况（Gas Price 太低）
- 显示预估手续费（ETH 计价 + 法币计价）

Gas 体验至今仍是 Web3 钱包最大的用户体验痛点之一。

## DApp 连接：钱包成为"身份"

### Web2 的登录

```
用户 → 输入用户名密码 → 服务器验证 → 登录成功
```

### Web3 的"登录"

```
用户 → 钱包签名一条消息 → DApp 验证签名 → 连接成功
```

钱包地址成了用户在 Web3 世界的身份标识。钱包不再只是资产管理工具，它变成了：
- **身份证**：证明你是某个地址的主人
- **通行证**：连接各种 DApp
- **签名笔**：授权各种链上操作

这个转变催生了 Web3 钱包最重要的交互模式：**Connect Wallet**。

## 以太坊早期的钱包方案

| 钱包 | 年份 | 形态 | 特点 |
|------|------|------|------|
| Mist | 2015 | 桌面全节点 | 以太坊官方钱包，内置 DApp 浏览器，2019 年停止维护 |
| MyEtherWallet (MEW) | 2015 | 网页端 | 纯前端，私钥不离开浏览器 |
| Parity Wallet | 2016 | 桌面全节点 | Rust 实现，后来出了著名的多签漏洞 |
| MetaMask | 2016 | 浏览器插件 | 改变了一切（下一篇详述） |
| imToken | 2016 | 移动端 | 中国市场最早的以太坊钱包之一 |

### Mist 的失败

以太坊基金会开发的 Mist 浏览器是一个有野心的项目——它想做"Web3 的浏览器"，内置钱包和 DApp 商店。但它失败了，原因包括：

- 全节点模式，同步慢、占用大
- 开发资源不足，bug 多
- 被 MetaMask 的轻量级方案碾压

Mist 的失败证明了一件事：**在 Web3 早期，轻量级 > 完整性**。用户要的是"能用"，不是"完美"。

## 范式转变的本质

以太坊对钱包的影响可以总结为一个词：**从被动到主动**。

- 比特币钱包是被动的：等待收款，发起转账，仅此而已
- 以太坊钱包是主动的：浏览 DApp、授权合约、参与治理、管理头寸

这个转变意味着钱包的设计复杂度指数级增长：

```
比特币钱包的状态空间：余额 × 交易历史
以太坊钱包的状态空间：余额 × 代币列表 × 授权状态 × DeFi 头寸 × NFT × 交易历史 × ...
```

## 小结

以太坊不只是给钱包增加了功能，它重新定义了"钱包"这个概念。钱包从一个存储工具变成了用户与整个可编程区块链交互的界面。这个范式转变带来了巨大的产品设计挑战，也创造了巨大的产品创新空间——MetaMask 正是在这个空间里崛起的。
