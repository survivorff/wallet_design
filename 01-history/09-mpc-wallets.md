# MPC 钱包：密钥分片与无助记词体验

## 一句话总结

把私钥拆成多个碎片，分散存储在不同地方，签名时各方协作计算——私钥从头到尾不以完整形态存在。

## 核心问题

传统钱包的安全模型有一个单点故障：

> 私钥是一个完整的数字，谁拥有它谁就拥有一切。

无论你把它存在纸上、硬件钱包里、还是手机的安全芯片中，它始终是一个完整的秘密。一旦泄露，就是 100% 的损失。

MPC（Multi-Party Computation，多方计算）的思路是：**让这个完整的私钥从来不存在。**

## MPC/TSS 的原理

### 什么是 TSS

TSS（Threshold Signature Scheme，门限签名方案）是 MPC 在数字签名领域的应用：

- 将签名能力分散到 n 个参与方
- 任意 t 个参与方（t ≤ n）协作即可生成有效签名
- 任何少于 t 个参与方无法生成签名，也无法推导出完整私钥

```
传统签名：
  私钥(完整) → 签名算法 → 签名

TSS 签名（2/3 门限）：
  分片1 + 分片2 → 协作计算 → 签名  ✅
  分片1 + 分片3 → 协作计算 → 签名  ✅
  分片2 + 分片3 → 协作计算 → 签名  ✅
  仅分片1 → 无法签名 ❌
  仅分片2 → 无法签名 ❌
  仅分片3 → 无法签名 ❌
```

### 与多签的区别

| | 多签（Multisig） | MPC/TSS |
|---|---|---|
| 实现层 | 链上（智能合约） | 链下（密码学协议） |
| 链上表现 | 多个签名，合约验证 | 一个标准签名，链无感知 |
| Gas 成本 | 更高（合约调用） | 与普通交易相同 |
| 链兼容性 | 需要链支持智能合约 | 任何链都可以（包括比特币） |
| 隐私 | 链上可见是多签 | 链上看不出是 MPC |
| 灵活性 | 修改规则需要链上交易 | 可以链下重新分片 |

### 关键流程

#### 1. 密钥生成（DKG - Distributed Key Generation）

```
参与方 A、B、C 共同执行 DKG 协议：
→ A 获得分片 a
→ B 获得分片 b  
→ C 获得分片 c
→ 对应的公钥 P 被计算出来
→ 完整私钥从未在任何地方出现过
```

#### 2. 签名（Threshold Signing）

```
A 和 B 想签名一笔交易：
1. A 和 B 各自用自己的分片进行本地计算
2. 双方交换中间结果（不暴露分片本身）
3. 经过多轮交互，生成最终签名
4. 这个签名与普通私钥生成的签名完全一样
```

#### 3. 密钥刷新（Key Refresh）

```
定期或按需刷新分片：
→ A 的分片 a 变成 a'
→ B 的分片 b 变成 b'
→ C 的分片 c 变成 c'
→ 公钥和地址不变
→ 旧分片即使泄露也无法使用
```

这是 MPC 相对于多签的独特优势——可以在不改变地址的情况下更新安全参数。

## MPC 钱包的典型架构

### 2/2 模式（用户 + 服务商）

```
┌──────────────┐          ┌──────────────┐
│   用户设备    │          │   服务商      │
│              │          │              │
│  分片 1      │ ←─协作─→ │  分片 2      │
│  (本地存储)   │          │  (服务器)    │
└──────────────┘          └──────────────┘
```

- 用户丢失设备：服务商协助恢复
- 服务商作恶：没有用户的分片无法签名
- 适合：个人用户，追求便利性

### 2/3 模式（用户 + 服务商 + 备份）

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│   用户设备    │   │   服务商      │   │   备份        │
│  分片 1      │   │  分片 2      │   │  分片 3      │
└──────────────┘   └──────────────┘   └──────────────┘

正常使用：分片1 + 分片2 协作签名
设备丢失：分片2 + 分片3 恢复
服务商不可用：分片1 + 分片3 自主操作
```

- 任何两方可以完成签名
- 单点故障不会导致资产丢失
- 适合：需要更高安全性的场景

### 机构级 MPC

```
┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐
│ 节点1│ │ 节点2│ │ 节点3│ │ 节点4│ │ 节点5│
└─────┘ └─────┘ └─────┘ └─────┘ └─────┘
    3/5 门限：任意 3 个节点协作即可签名
    
    节点分布：不同地理位置、不同云服务商、不同管理员
```

适合：交易所、基金、托管商

## MPC 钱包的优势

### 对用户

1. **无助记词**：不需要备份 12 个词，降低认知门槛
2. **可恢复**：设备丢失可以通过其他分片恢复
3. **渐进式安全**：可以从 2/2 升级到 2/3
4. **跨链通用**：MPC 在链下完成，支持任何链

### 对机构

1. **消除单点故障**：没有一个人能独自转走资金
2. **合规友好**：可以实现审批流程、权限分级
3. **审计追踪**：每次签名都有参与方记录
4. **灵活策略**：可以根据金额设置不同的门限

## MPC 钱包的问题

### 技术层面

- **协议复杂度**：MPC 协议实现难度高，bug 可能导致资金损失
- **通信开销**：签名需要多轮交互，延迟比本地签名高
- **活性依赖**：需要多方同时在线才能签名
- **审计困难**：MPC 协议的正确性验证比智能合约更难

### 信任层面

- **服务商依赖**：2/2 模式下，服务商不可用 = 无法签名
- **代码不透明**：很多 MPC 实现不开源
- **"无助记词"的代价**：用户失去了完全自主的能力
- **监管风险**：服务商可能被要求冻结或配合执法

### 与账户抽象的关系

MPC 和 AA（账户抽象）不是竞争关系，而是互补的：

```
MPC 解决的问题：密钥管理（如何安全地持有和使用签名能力）
AA 解决的问题：账户逻辑（账户可以做什么、怎么验证、怎么执行）

组合使用：
MPC 管理密钥分片 + AA 提供可编程账户逻辑
= 既安全又灵活
```

## MPC 的适用场景

| 场景 | 为什么适合 MPC |
|------|--------------|
| 新用户 Onboarding | 无助记词，社交登录即可创建钱包 |
| 机构资金管理 | 多方审批，消除单点故障 |
| 嵌入式钱包 | 开发者集成简单，用户无感 |
| 跨链操作 | 一套分片管理所有链的密钥 |
| 高频交易 | 比链上多签更快（无需等区块确认） |

## 小结

MPC 钱包代表了密钥管理的一次范式转变：从"保护一个完整的秘密"到"让秘密从不完整存在"。它特别适合两类场景：需要极致便利的个人用户（无助记词体验）和需要极致安全的机构用户（多方协作控制）。

但 MPC 不是银弹。它引入了新的信任假设（对服务商的依赖）和新的技术风险（协议实现的正确性）。在钱包的安全方案选择中，MPC、多签、硬件钱包、AA 各有适用场景，未来更可能是组合使用而非互相替代。
