# AllScale 剖析：建在 Turnkey 上的自托管稳定币新银行

## 一句话总结

AllScale 证明了一件事：当 Turnkey 这类基础设施把自托管的工程成本压到可承受，一个七人量级的团队也能在一年内做出 150 万钱包、把"不托管用户资金"从理想变成商业上可行的默认选项。

## 基本档案

| 项目 | 信息 |
|---|---|
| 定位 | 自托管稳定币新银行（self-custodial stablecoin neobank） |
| 总部 | 加拿大温哥华 |
| 上线时间 | 2025 年 5 月 |
| 融资 | 种子轮 $6.5M（其中 $5M 由 YZi Labs 领投，Informed Ventures、Generative Ventures 参投；Animoca Brands 后续投资） |
| 规模 | 1.5M+ 用户钱包，日交易额 $500K+，上线以来用户增长 10 倍 |
| 钱包基础设施 | **Turnkey** |
| 目标客群 | 全球中小企业、自由职业者、创作者、AI Agent |
| 法律定位 | 明确声明是金融技术开发商，不是银行，不提供数字资产托管服务 |

## 为什么这家值得单独剖析

AllScale 本身规模不大，但它在这本知识库里的价值是**一个完整的对照实验**：

```
问题：自托管的用户体验能不能做到和 Web2 Fintech 一样好？

传统答案：不能。
  用户要装钱包、记助记词、理解 gas、每笔交易签名
  → 转化率崩掉

AllScale 的答案：能，只要你不自己造轮子。
  把密钥管理、认证、策略、会话签名全部外包给 Turnkey
  自己只做产品层：发票、工资单、Checkout、Claim Link
  → 1.5M 钱包，10 倍增长
```

它同时也是理解"基础设施层如何改变应用层可行策略"的最佳案例（这个论点在 [00-market-landscape](./00-market-landscape.md) 里展开过）。

## 技术架构

### 整体分层

```
        ┌──────────────────────────────────┐
        │  AllScale 产品层（自建）           │
        │  发票 / 工资单 / Checkout /       │
        │  Claim Link / 收益                │
        └───────────────┬──────────────────┘
                        │
        ┌───────────────▼──────────────────┐
        │  Turnkey（外包）                  │
        │  安全飞地密钥管理                  │
        │  Passkey / 邮箱 / Google 认证      │
        │  策略引擎（限额 + 时间窗）           │
        │  会话签名                         │
        │  Claim Links                     │
        └───────────────┬──────────────────┘
                        │
        ┌───────────────▼──────────────────┐
        │  链上：USDC / USDT 多链           │
        └──────────────────────────────────┘
```

### 关键决策一：从"自建 Passkey 系统"转向外包

这是创始团队自己讲出来的一段经历，很有参考价值。

```
早期：团队自己搭了一套基于 Passkey 的认证系统
      技术上是能跑的

为什么放弃自建：
  1. Turnkey 已建立的安全信誉是战略优势
     （对一个做资金业务的新公司，"谁在管密钥"
       是客户会问的第一个问题）
  2. 用户设备和操作系统五花八门，
     Passkey 支持度按手机品牌和系统版本差异很大
     → 自己适配是无底洞
  3. 长期看，自建密钥基础设施会带来
     显著的安全、合规、运维负担
```

**这段判断值得任何做钱包类产品的团队抄下来**：自建密钥管理的成本不在"能不能跑通",而在"能不能长期维护 + 能不能让客户相信"。

### 关键决策二：多种认证方式并行

```
Passkey  +  邮箱  +  Google 登录

为什么必须三条都要：
  目标市场是非洲、东南亚、拉美
  → 设备碎片化严重
  → Passkey 兼容性无法保证
  → 必须有退路

结果：创建非托管钱包的体验 ≈ 登录一个 Fintech App
      不需要下载外部钱包，不需要手动管私钥
```

### 关键决策三：用策略引擎 + 会话签名消灭签名疲劳

这是 AllScale 最实用的一个技术选择。

```
业务现实：
  用户一天内会发/收多笔小额支付
  （开发票、结算电商订单）

如果每笔都弹窗签名：
  → 高频商家直接放弃

解决方案：
  Turnkey 的会话签名（sessions）
  + 策略引擎定义交易限额和时间窗

效果：
  在限额和时间窗内，多笔链上操作不需要逐笔确认
  安全性由策略引擎在飞地内强制保证
```

创始人对这一点的评价大意是：这单枪匹马消除了逐笔签名的需求，同时保持了安全，对新接触加密支付的用户是决定性的改善。

**架构上值得注意的是**：这里的安全性不是靠"用户每次确认"，而是靠"预先定义的策略在飞地内强制执行"。这是一种范式转移——**从"人工授权每笔"变成"程序化授权规则"**。（对照 [03-product-design/04-transaction-confirmation](../03-product-design/04-transaction-confirmation.md)）

### 关键决策四：非托管状态的技术保障

```
AllScale 宣称非托管，凭什么？

Turnkey 的子组织模型：
  AllScale = 父组织
  每个用户 = 一个完全隔离的子组织
  父组织对子组织只有读权限，不能修改

所以：
  AllScale 在架构上就动不了用户的钱
  → "非托管"不是法律声明，是系统事实
```

这也是 AllScale 敢在官网明确写"不提供数字资产托管服务"的底气。

### 产品功能：Claim Link

2026 年 8 月上线的功能，技术上基于 Turnkey 的 claim links：

```
场景：给一个还没有钱包的人转钱

流程：
  发送方从余额生成一个领取链接
        ↓
  发给任何人（微信、邮件、WhatsApp）
        ↓
  收款方两个选择：
    a) 填入 0x 地址领取
    b) 用邮箱现场创建 AllScale 钱包领取

同一套机制还被用来实现链上退款
```

**为什么这个功能重要**：它解决了稳定币支付最后一个 Onboarding 障碍——收款方也需要有钱包。有了 Claim Link，付款方不需要等收款方先准备好。

## 业务架构

### 产品线

| 产品 | 场景 | 收入方式 |
|---|---|---|
| **Invoice**（一次性发票） | 自由职业者/小企业开票收款 | 交易抽成 |
| **Payroll**（工资单） | 全球远程团队发薪 | 交易抽成 |
| **Checkout** | 商家收款，支持信用卡 / Apple Pay / 链上 | 支付通道费差 |
| **Claim Link** | 向无钱包用户转账、退款 | 交易抽成 |
| 余额收益 | 稳定币持有 | 利差 |

### Checkout 的关键设计：法币入口 + 稳定币结算

```
买家可以用：信用卡 / Apple Pay / 本地支付方式 / 链上
商家收到的：稳定币，实时结算

价值主张：
  ✅ 保留加密支付好的部分
     - 即时全球结算
     - 链上无拒付
     - 钱包里只有一种币，不用管汇率
  ❌ 去掉不好的部分
     - 不要求每个买家都已经持有代币
```

这是稳定币支付走向主流的关键设计模式：**买家侧完全 Web2，卖家侧完全稳定币**。（可对照 [09-future/07-wallet-and-payments](../09-future/07-wallet-and-payments.md)）

### 商业模式判断

```
收入来源（推断，未公开披露明细）：
  1. 交易抽成（发票、工资单、Checkout）
  2. 卡/本地支付通道的费率差
  3. 稳定币余额的收益利差
  4. 未来可能：企业订阅、API 授权

成本结构：
  - Turnkey 的签名费用（按签名计费）
  - 支付通道成本（卡收单是最贵的一块）
  - Gas（多链稳定币转账）
  - 合规与风控
```

**一个值得注意的单位经济问题**：

```
日交易额 $500K，1.5M 钱包
→ 人均日交易额约 $0.33

如果按 1% 抽成，日毛收入约 $5,000
→ 年化约 $180 万毛收入

同时 1.5M 钱包每月产生的签名量
在 Turnkey 按签名计费下是一笔实在的成本。

结论：现阶段是典型的「用户增长快、单用户价值低」的阶段。
      要盈利，要么提高人均交易额（往 B 端企业客户走），
      要么增加高毛利产品（收益、卡）。
```

这也解释了为什么产品线在往企业发票、工资单、Checkout 这些**客单价更高的 B 端场景**扩展ï¼而不是继续做 C 端转账。

### 落地案例：Bravo Rewards

```
AllScale Checkout 已集成 Bravo Rewards
→ 覆盖温哥华 450+ 家餐厅的稳定币餐饮支付

关键点：用户和商家都不需要接触底层技术
       → "让区块链隐形"从口号变成了可验证的落地
```

从大温哥华本地场景切入是合理的策略——**先在总部所在地做出可展示的密度，再复制**。

### AI Agent 支付：值得关注的定位

```
AllScale 明确支持可编程的机器对机器支付：
  AI Agent、智能合约、自主工作流

为什么这个定位对它有利：
  Agent 支付的核心需求 = 程序化授权 + 硬约束
  而它的底层（Turnkey 策略引擎 + 会话签名）
  正好就是为这个设计的

→ 同一套技术栈同时服务人类高频支付和 Agent 支付，
  边际成本几乎为零
```

（可对照 [09-future/03-ai-agent-wallets](../09-future/03-ai-agent-wallets.md)）

## 批判性分析

### 优势一：自托管在这个客群里是真实卖点

```
目标客群：非洲、东南亚、拉美的自由职业者和小企业

他们的真实恐惧不是"资产不够去中心化"，
而是"账户被冻结"和"平台跑路"。

→ 自托管直接回答这个恐惧
→ 对比 Infini 的托管路线（见 06-infini）,
  在这个客群里说服力更强
```

### 优势二：外包基础设施带来的速度

```
团队小 + 基础设施外包
→ 工程精力全部投在产品差异化上
→ 上线一年内做出 Invoice、Payroll、Checkout、Claim Link
  四条产品线 + 10 倍增长

这是「买 vs 建」决策的正面教材。
```

### 局限一：对 Turnkey 的深度依赖

```
风险清单：
  ⚠️ Turnkey 涨价 → 成本结构直接受冲击
     （按签名计费，AllScale 是高频场景）
  ⚠️ Turnkey 被收购/转向 → 路线图受影响
  ⚠️ Turnkey 停机 → AllScale 全线不可用
  ⚠️ 迁移成本：Turnkey 的钱包是飞地内 HD 种子，
     换供应商要处理地址体系迁移
     （这正是 Crossmint 攻击的点，见 04-crossmint）

缓解：
  ✅ 用户资产在链上，Turnkey 不能挪用
  ✅ 理论上可导出种子迁移
  但"理论上可迁移"和"实际迁移 150 万钱包"是两件事。
```

### 局限二：单位经济还没跑通

前面算过：人均日交易额约 $0.33。这个数字在早期增长期可以接受ï¼但**要证明商业模式必须让它上升一到两个数量级**。路径要么是客群升级（从个人到企业）,要么是场景升级（从转账到收单/发卡/收益）。

### 局限三：合规敞口

```
"金融技术开发商，不是银行，不提供托管服务"
这个定位在监管上是防御性的，但不是免疫的。

真实敞口：
  - 跨境支付涉及汇款牌照（各司法区不同）
  - Checkout 涉及支付收单资质
  - 目标市场（非洲、东南亚、拉美）监管环境多变
  - 收益产品可能触发证券认定

自托管确实降低了"托管"这一项的监管负担，
但"支付"这一项躲不掉。
```

### 局限四：规模仍然很早期

```
对照同赛道的领先者：
  KAST：$80M A 轮，100 万+ 用户，年化交易额约 $50 亿
  AllScale：$6.5M 种子，150 万钱包，日交易额 $50 万
            （年化约 $1.8 亿）

钱包数相当，交易额差约 27 倍。
说明 AllScale 的钱包"更浅"——注册多，重度使用少。

这也验证了前面的单位经济判断。
```

## 小结

AllScale 最有价值的地方不是它的规模ï¼而是它证明了一个此前存疑的命题：**自托管可以做到和托管一样好的体验ï¼而且做这件事不需要一个大团队**。

它的做法很纯粹——把所有和密钥、认证、策略相关的重活外包给 Turnkey,自己只做产品层的差异化（发票、工资单、Checkout、Claim Link）。结果是一年内四条产品线加十倍增长。这是"买 vs 建"决策里最清晰的正面案例。

它的挑战也很清晰：单位经济还没跑通（人均日交易额不到半美元）,对单一供应商的依赖很深ï¼而且在这个赛道里已经有拿到 $80M A 轮、年化交易额高一个数量级的对手。

往后看ï¼值得盯的是两件事：**人均交易额能不能上一个数量级**,以及**它会不会在某个时点必须自建或多供应商化以控制成本**。第二件事的答案ï¼很大程度上决定了 Turnkey 这类"卖底层能力"的商业模式能不能长期留住成长起来的客户。
